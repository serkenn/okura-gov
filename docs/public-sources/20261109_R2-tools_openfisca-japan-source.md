## 2. 報告書の主張とコードの対応

報告書：`references/govtech-tokyo_openfisca_report_2025-04-16.pdf`（以下「報告書」）。

### (a) グループエンティティは「世帯」だけか → **成り立つ**

- `openfisca_japan/entities.py:11-50` で `世帯`（グループエンティティ）、`:52-67` で `人物`（`is_person = True`）を定義。`:69` `entities = [世帯, 人物]`。グループは `世帯` の1種類だけ。
- `世帯` の label は "All the people in a family or group who live together in the same place."（`entities.py:14`）。同居が前提の定義。
- 報告書 p.18「OpenFisca-Japan では『グループ』エンティティは同居している家族として『世帯』のみ定義しています」と一致する。
- 帰結の実例：`openfisca_japan/variables/所得.py:512-516` に「TODO: 『同居していない親族』も世帯内で扱うようになったら同居老親かどうかの判定追加」とあり、同居していない親族を扱えないことをコード自身が認めている。
- entities.py の役割部分の最終変更は `509d11c`（2024-01-03、flake8 対応）。報告書の時点（v1.3.0、2025-04-22）から変わっていない（`git diff --stat v1.3.0 HEAD -- openfisca_japan/entities.py` が空）。

### (b) 役割の一覧と「子」は未成年だけか → **役割の一覧は成り立つ。「子は未成年だけ」はコードでは強制されておらず、成り立たない**

- 役割は3つ（`entities.py:29-49`）：
  - `親`（`max: 2`、doc「大人あるいは子を持つ親」、`:31` のコメント「子供がいない場合も大人は『親』entityとする」）
  - `子`（上限なし、doc「親と同居している子供」`:41`）
  - `祖父母`（上限なし、doc "Other individuals living in the 世帯."）
- `子` の定義に **年齢の制限はない**。entities.py にも、`子` を検証する変数にも、未成年に限る処理は見当たらない（`成人年齢` パラメータ `openfisca_japan/parameters/全般/成人年齢.yaml` を参照しているのは `variables/福祉/生活保護.py:1455` の未成年者控除だけ）。
- テストでは成人の `子` を使っている：`openfisca_japan/tests/所得/扶養控除.yaml` の「扶養控除（特定扶養親族の年齢下限）」（19歳、`:265-289`）、「特定扶養親族の年齢上限」（22歳、`:291-316`）。いずれも `子一覧` に入れた 19〜22歳の人で特定扶養親族の扶養控除を計算している。このテストは `2e0b0ec`（2023-10-14「扶養控除を追加」）からある。
- フロントエンドも、子どもの区分に「高校卒業後相当」（`minAge: 16, maxAge: 999`）を持ち（`dashboard/src/components/questions/template/childrenAgeQuestionTemplate.tsx:67-75`）、入力された子どもはすべて `子一覧` に入れる（`dashboard/src/state/convert.ts:1181-1182`）。報告書の時点の v1.3.0 にも同じ区分がある（`v1.3.0:dashboard/src/components/forms/attributes/SchoolYear.tsx:83-86`）。
- 報告書 p.19 の記述は「子：未成年。成人であっても未成年の兄弟姉妹がいる場合はこのロールとなる」であり、これは **役割を割り当てるときの運用上の約束** の説明と読める。報告書自身も「子どもに対する制度の実際の実装では、念の為『子』のロールと年齢を参照している」と書いている（p.19）。
- まとめ：「19〜22歳の特定扶養親族を『子』として扱えない」（HANDOFF.md §4）は、現在のコードでは成り立たない。ただし役割は「回答者（あなた）から見た世代」で割り当てられ、同居が前提で、`親` は最大2人という制約は残る。

## 3. 参考になる部分（自作パッケージを書くとき）

コードはコピーしない（AGPL。§4）。考え方だけを参考にする。

- **パラメータの YAML の構成**：1ファイル1パラメータで、`description`、`metadata.reference`（出典URL）、`metadata.unit`、`values:` の下に施行日をキーにした値を並べる（例 `parameters/全般/成人年齢.yaml:1-11`：`1876-01-01: 20.0`、`2022-04-01: 18.0`。施行日ごとのコメントつき）。値ごとに `metadata.reference` をつける書き方もある（`parameters/所得/扶養親族所得金額.yaml:8-9`）。ディレクトリが名前空間になり、`parameters(対象期間).所得.扶養控除_一般` のように参照する（`variables/所得.py:524-527`）。ディレクトリに `index.yaml` を置いて説明をつけられる（`parameters/福祉/index.yaml`）。
- **施行日による計算式の切り替え**：`formula_2025_01_01` のように、メソッド名に施行日をつけて計算式を分ける（`variables/所得.py:578, 601, 630`）。ただし税率表（`所得.py:861-883` の基準所得税額の税率と控除額）や給与所得控除の段階（`所得.py:179-189`）は計算式に直書きされ、パラメータになっていない。自作ではパラメータ（YAML の scale など）に出すべき点の反面教師になる。
- **大きい表は CSV**：配偶者控除額などは `assets/所得/*.csv` を `np.genfromtxt` で読み、`@cache` で保持している（`variables/所得.py:131-163`）。ただし CSV には施行日の仕組みがない。
- **期間の扱い**：所得・収入は `definition_period = DAY` で定義し、`set_input = set_input_divide_by_period` で年額の入力を日に按分している（`variables/所得.py:25-34, 50-59`）。年齢は「その年の12月31日時点」を `period(f"{対象期間.start.year}-12-31")` で取る（`所得.py:502-505`）。暦年の税と特定日の手当を同じ変数で扱うための工夫だが、年額を日に割る近似でもある。
- **テストの書き方**：`tests/` 配下の YAML に `name`・`period`・`input`（`世帯:` に役割ごとの一覧、`世帯員:` に各人の値）・`output` を書く（`tests/所得/扶養控除.yaml:1-19`）。境界値（480000 と 480001）を並べる書き方は参考になる（`:1-39`）。実行は `openfisca test --country-package openfisca_japan openfisca_japan/tests`（`Makefile:45-46`）。
- **日本語の名前**：変数名（`class 扶養控除(Variable)`）、引数名（`対象人物, 対象期間`）、エンティティの key（`世帯`、`人物`）、役割（`親`・`子`・`祖父母`）、パラメータのファイル名・ディレクトリ名（`parameters/所得/扶養控除_一般.yaml`）まで日本語で書かれ、そのまま動く前提で配布されている（PyPI 2.2.0）。
- **名前の衝突の回避（接頭辞）**：住民税の控除には「住民税」を付ける。理由がコメントに書かれている：「OpenFiscaではクラス名をアプリ全体で一意にする必要があるため、先頭に『住民税』を追加。」（`variables/住民税.py:289`）。同様に `特別児童扶養手当の控除後所得`（`variables/所得.py:821`）。報告書 p.17-18 の記述と一致。
- **条件の書き方**：`np.select`、`np.where`、`*`（and）、`+`（or）、`np.logical_not` で配列のまま条件を書く（`所得.py:519-528`、`:424` のコメント「複数世帯のarrayのためand, orの代わりに *. +」）。報告書 p.28-29 の「if 文を使わず掛け算で条件を表す」の実例。

## 5. 安全性で気になった点（静的に読んだ範囲）

- **計算パッケージ本体（`openfisca_japan/`）**：`eval(`・`exec(`・`__import__`・`subprocess`・`os.system`・`pickle`・`yaml.load(`・ネットワーク送信（`requests.`・`urllib`・`socket`）は見当たらない。動的な import は開発用ツールだけ（`tools/dependency_graph/dependency.py:109` が自パッケージの .py を import、`tools/make_tests/mylib/utils.py:24` が `.mymodule.` 配下を import）。`reforms/add_dynamic_variable.py:17-28` は `type()` で Variable を作るテンプレートの名残（固定の値だけで、外部入力は使わない）。
- **待ち受けアドレス**：`Makefile:48-52` で `openfisca serve ... --bind 0.0.0.0:50000`（serve-local）と `--bind 0.0.0.0:8080`（serve-public）。`docker-compose.yml:11-12` は `ports: - 50000:50000` で、ホスト側のアドレスを指定していないため、Docker の既定ではホストの全インターフェイスで公開される。swagger-ui も `8080:8080`（`docker-compose.yml:33-34`）。所得などの機微な情報を流すなら、このまま使うと LAN に公開される。
- **フロントエンドの外部送信**：`dashboard/index.html:9-11, 73` で Google Tag Manager を読み込む。`docker-compose.yml:22` に開発用の GTM ID の既定値がある。フロントエンドの既定の API 接続先は外部の Cloud Run（上記）。本プロジェクトはフロントエンドを使わないので直接の影響はないが、参考として記録する。
- **`Makefile:3-4` の `uninstall`**：`pip freeze | grep -v "^-e" | xargs pip uninstall -y`。誤った環境で実行すると、その環境のパッケージをすべて消す。
- **古い依存**：§4 のとおり、Core 41 系に固定され、`requirements.txt` に既知の脆弱性が多い版が並ぶ。使うなら依存を更新する必要がある（本プロジェクトは D6 により使わない）。
- **AI エージェント向けの指示ファイル**：`.claude/commands/*.md` と `.agents/skills/*/SKILL.md` がリポジトリに含まれる。clone したディレクトリでエージェントを起動すると、これらが指示として読み込まれる可能性がある。本調査ではエージェントの指示としては扱わず、内容も読んでいない。
- 致命的な問題（外部からの入力で任意のコードが実行される経路、勝手な外部送信）は、計算パッケージ本体には見当たらなかった。待ち受けの既定値（0.0.0.0）は、そのまま使うと危険な既定値に当たる。
