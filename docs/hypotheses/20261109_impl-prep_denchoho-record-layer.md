## H1. 記録層は「誰が電帳法第7条の保存義務者か」を判定しない。全員・全証憑に最も厳しい扱いを一律にかける

- 根拠：電子取引データの保存義務があるか（法第7条）、何年保存するか（L9・L10）は、所得区分（事業所得か業務に係る雑所得か）、青色か白色か、前々年の業務の収入金額（300万円）に依存する（[PS-D] §1・§2.9・§5）。これらは法的な判断で、記録層の外（判定コア）の仕事。前々年300万円以下の人や給与だけの人が対象外であることを明示した一次情報も見つかっていない（[PS-D] §8）。
- 提案：
  1. 記録層は、家族の全員について、取引に関して電子で受け取った・送ったデータを、L1〜L8 を満たす方法で全部保存する（人ごとに区分する）。
  2. 保存期限は、所得区分を問わず一律に長いほう（§H5）を使う。短くしてよいかは、判定コアが出す「保存義務の判定」（所得区分・前々年の収入金額から）と人の判断（D12）で決める。
  3. 判定コアには「電帳法第7条の対象者か」「検索要件の免除に当たるか（基準期間の売上高5,000万円以下）」を、所得税の計算とは別の出力として持たせる。記録層はその結果を参照して表示するだけ。

## H2. 証憑ファイルは受け取ったまま、台帳と分けて、内容のハッシュで識別して保存する

- 根拠：L8（自分で入力した取引情報は保存にならない。手動転記は合理的な編集に当たらない）。beancount の取引は人が入力した記録なので、それだけでは電子取引データの保存にならない（[PS-D] §2.7）。beancount の `document` ディレクティブは取引と直接つながらず、メタデータかリンクで結ぶ必要がある（[PS-PTA] §1.5・§1.6、[M-BC] §7）。`option "documents"` の自動走査は日本語のディレクトリ名を無視する（[M-BC] §7）。
- 提案：
  1. 証憑ストア：`evidence/<人のID>/<年>/` に、受け取ったバイト列のまま置く。識別子は SHA-256（`evidence_id = "sha256:<hex>"`）。元のファイル名・受領日時・取得経路（メール・ウェブ・クラウド・アプリ・ネットバンキング等）は、ファイル名ではなく証憑の記録（H3 のログ）に持たせる。
  2. 合理的な編集（PDF 化、パスワード解除、HTML の PDF 化、複数請求書の PDF の分割）をした場合は、元のファイルも残し、編集後のファイルに `derived_from: <元の evidence_id>` と編集の種類を記録する。手で書き写したもの（OCR の結果を含む）は証憑として扱わない。
  3. メールは、本文に取引情報があればメール（.eml）を、添付で授受したなら添付ファイルを保存（Q&A（取引）問6・問36、[PS-D] §2.7・§2.8）。
  4. 台帳（beancount）の取引には決まった語彙のメタデータ `evidence: "sha256:…"`（複数可）を付け、証憑と取引を結ぶ。beancount の `document` ディレクティブと `option "documents"` は使わない（安全な読み込みの対象外にする理由はないが、`document` は取引と直接結べず、`option "documents"` の自動走査は日本語のディレクトリ名を黙って無視するため。`document` ディレクティブ自体は日本語のファイル名でも動く。[M-BC] §7）。
  5. ウェブ上で随時確認できる EC サイト・ネットバンキングの明細は、ダウンロードしなくてもよい場合がある（問11・問45）が、保存期間の満了まで確認できる保証はないので、記録層ではダウンロードして保存する（保守的な既定）。

## H3. 真実性は規則第4条第1項第4号（事務処理規程）で満たし、追記のみのハッシュ連鎖ログを規程の運用の記録にする

- 根拠：L3。第1号・第2号は総務大臣が認定する時刻認証業務のタイムスタンプが必要（[PS-D] §2.2）。第3号はデータの **授受も** そのシステムで行う必要があり、メールやウェブからのダウンロードのように授受がシステムの外で起きる場合は当たらない（問43）。家族の個人利用の範囲では第4号が現実的で、国税庁が個人事業者用のひな形を出している（[PS-D] §6.1）。通達7-7 は、第4号の規程に当たるものの例として、① 訂正削除の原則禁止、② 訂正削除の手続（日付・理由・内容・担当者の記録と保存）、③ 責任者の明確化 を含む規程を挙げる（「例えば…内容を含む規程がこれに該当する」。[PS-D] §6.2）。ハッシュの記録は法令上の要件ではない（L3 の4つに入っていない）。
- 提案：
  1. 人（保存義務者）ごとに、国税庁の「個人事業者の例」をもとにした事務処理規程を `records/<人のID>/kitei.md` として置き、施行日を書く。規程に、データ管理責任者・処理責任者（親が運用する場合はその旨）を書き足す（通達7-7(1)③）。
  2. 追記のみのログ `records/<人のID>/evidence-log.jsonl`：1行1件。種類は `received`（受領・保存）、`derived`（合理的な編集）、`correction_request`（訂正削除の申請）、`deleted`（保存期限経過後の廃棄）。`correction_request` には規程のひな形の8項目（申請日、取引伝票番号＝取引ID、取引件名、取引先名、訂正・削除日付、訂正・削除内容、訂正・削除理由、処理担当者名）を必須の欄として持たせる。
  3. 各行に、前の行の SHA-256 を入れる（ハッシュ連鎖）。証憑ファイルの SHA-256 も入れる。検証コマンドが、ファイルの存在・ハッシュの一致・連鎖の切れ目を報告する。
  4. 証憑の上書き・削除は記録層の API ではできないようにする（ファイルを作ったら読み取り専用にする。削除は保存期限の経過と人の判断（D12）の両方を要件にし、`deleted` をログに残す）。
  5. ハッシュ連鎖は、それだけでは本人による全面的な作り直しを防げない（I3 で検討）。法令上の真実性は規程とその運用で満たし、ハッシュは運用の記録・事故の検知の道具と位置づける。

## H4. 検索は、免除に当たる見込みでも、日付・金額・取引先の索引を自動で作って持つ

- 根拠：L5。基準期間の売上高5,000万円以下でダウンロードの求めに応じれば検索要件は不要だが、それは判定期間ごとの事実に依存し（新規開業は基準期間がなく不要）、判定の誤りの影響が大きい。システムがなくても、索引簿かファイル名の規則で満たせる（通達4-12、問19・問50、[PS-D] §2.5）。猶予措置や免除の(b)は、日付・取引先ごとに整理した出力書面の提示を前提にする（[PS-D] §2.4・§2.6）。
- 提案：
  1. 索引の列（証憑ごと）：`evidence_id`、`person`、`date`（取引年月日その他の日付。利用明細のように複数の取引をまとめたデータは発行日）、`amount`（データに記載された金額。まとめたデータは合計。金額がなければ空欄）、`counterparty`（取引先）、`doc_type`（請求書・領収書・利用明細・振込明細など）、`tx_ids`（台帳の取引ID）、`received_at`、`source`。日付と金額の決め方は課税期間の途中で変えない（問55・問56）。
  2. 索引は H3 のログと台帳のメタデータから機械的に作る（台帳の金額を証憑の金額として使わない。証憑の金額は受領時に人が読んで記録する「事実」で、取引の金額とは別の欄）。
  3. 範囲指定（日付・金額）と2項目以上の AND を持つ検索コマンドを用意する（beanquery を使うか、索引の CSV に対する小さな検索。どちらでも要件の形は同じ）。
  4. 保険として、保存時のファイル名にも規則性を持たせる：`<YYYYMMDD>_<取引先>_<金額>_<sha256の先頭8桁>.<拡張子>`（西暦に統一。問50 の注意）。ファイル名は受領時に決め、後から変えない。

## H5. 保存期限は証憑ごとに計算して記録し、最長の7年を既定にする

- 根拠：L2・L9〜L11。起算日は書類なら作成・受領の日の属する年の翌年3月15日の翌日、帳簿なら閉鎖の日の属する年の翌年3月15日の翌日（所規第63条第4項）。白色の書類・雑所得の書類は5年、青色の現金預金取引等関係書類と帳簿は7年（[PS-D] §5）。医療費の領収書は確定申告期限の翌日から5年（所法第120条第5項）。期間の満了は民法第143条で計算する（[PS-R1] §3）。国税通則法第10条第1項第2号・第3号も同じ計算で、所規の期間にどちらが適用されるかは一次情報で確認できていない（[PS-D] §5.5）。
- 提案：
  1. 証憑ごとに `retain_from`（起算日）と `retain_until`（既定は起算日から7年）を索引に持つ。所得区分が判定された後に短くするのは人の判断（D12）でだけ行う。
  2. 起算日と満了日の計算は名前つきの関数（例：`kisanbi_shorui(受領日)`、`manryo(起算日, 年数)`）にして、法令の出典を付ける（D13 と同じ扱い）。
  3. 台帳（beancount）は年ごとに閉じ、その年の台帳の保存期限も同じ方法で記録する。

## H6. 見読性とダウンロードの求めへの対応を、エクスポートのコマンド1つにまとめる

- 根拠：L4・L5（ダウンロードの求めに一部でも応じないと緩和は受けられない。通達4-14、問59 は「通常出力できるであろうファイル形式等」）。猶予措置は電子データと出力書面の両方の提示が要件（[PS-D] §2.6）。出力書面は課税期間ごとに日付順→取引先ごと、などで整理（通達7-3）。
- 提案：`export --person <人> --year <年>` が次を作る：(a) その年の証憑ファイルの原本一式（元のファイル名つきの写し）、(b) 索引の CSV（UTF-8）、(c) 日付順・取引先順に並べた一覧の PDF か HTML（印刷用）、(d) 事務処理規程と H7 のシステム概要書、(e) H3 のログとその検証結果。暗号化して保管する場合も、エクスポートは復号した状態で出す（通達7-1(1) は暗号化されたままではなく出力できることを求める）。

## H7. okura-gov 自身の「システム概要書」と「事務手続の書類」を docs として備え付ける

- 根拠：L6（自己開発のプログラムを使うなら、電子取引データについてもシステム概要書が要る）。帳簿を電子で保存する場合は、システム概要・開発時の書類・操作説明書・事務手続の書類（規則第2条第2項第1号イ〜ニ。他人が開発したプログラムだけならイ・ロ不要）。書面以外（オンラインマニュアル等）で備え付けてもよい（通達4-6、[PS-D] §3）。家族が開発したプログラムが「保存義務者が開発したプログラム」に当たるかは不明（[PS-D] §8）。
- 提案：当たる前提で、リポジトリに (1) システム概要（取得→証憑ストア→ログ→索引→台帳→中間表現→判定コアのデータの流れ）、(2) 操作説明（受領・訂正申請・検索・エクスポートの手順）、(3) 事務手続（入力の期日、確認、訂正削除の承認と記録、責任者）を置き、版をつける。国税庁の帳簿用サンプル（Q&A（帳簿）問9）の項目（入力担当者、入力期日、入力内容の確認、管理責任者の確認、訂正削除の承認と記録）をそろえる。

## H8. 帳簿（beancount 台帳）は、既定では「年末に紙へ出力して保存」とし、電子保存は条件がそろったときの選択肢にする

- 根拠：L12。電子データのまま帳簿を保存できるのは正規の簿記の原則（一般的には複式簿記）に従う帳簿に限られ、最初の記録段階（原則として課税期間の初日）から一貫して電子で作成する必要がある（[PS-D] §3）。beancount は複式簿記の形式だが、白色申告者の台帳が「正規の簿記の原則に従い…記録されているもの」に当たるかの一次情報はない（[PS-D] §8）。コンピュータで作成した帳簿を紙に出力して保存する方法は、Q&A の図で認められている（[PS-D] §3 の「帳簿書類等の保存方法」の図）。
- 提案：
  1. 既定：各年の台帳を年が明けたら（遅くとも確定申告の前に）整然とした形式で紙に出力し、その年の帳簿として保存する（7年）。電子の台帳は作業用として残す。
  2. 電子保存を選ぶ場合の条件：その年の1月1日から beancount で記帳している、資産・負債・資本に影響する一切の取引を複式で記録している、H6・H7 を満たしている。満たしているかは人の判断（D12）として記録する。
- 証憑（書類）は H2〜H6 で電子のまま保存する（紙で受け取ったものは紙で保存。スキャナ保存は任意の制度で要件が別なので、初期の範囲に入れない。[PS-D] §4）。

## H9. 重加算税の加重措置の除外（令和8年分から）とタイムスタンプは、初期の範囲に入れない

- 根拠：L13 は国税庁長官の基準に適合する特定電子計算機処理システム（デジタル庁が管理する仕様（Invoice JP PINT・JP Self-Billing）に従った電子インボイス＝国税庁の資料の呼び方で Peppol インボイス、又は預貯金口座の決済データ）と事前の届出を要する（[PS-D] §1）。加重措置は隠蔽・仮装があった場合の話で、保存の要件ではない。タイムスタンプは外部の認定事業者のサービスが必要（[PS-D] §2.2）。
- 提案：記録層の設計はこれらを前提にしない。将来使う場合に備え、証憑の記録に `source`（取得経路）を持たせておく（H2）。

## H10. 記録層のスキーマに足す語彙（事実だけ）

- 根拠：H2〜H5。D3（記録は事実だけ）、D11（決まった語彙のメタデータをスキーマで検査）。
- 提案（JSON Schema で定義する語彙の候補）：
