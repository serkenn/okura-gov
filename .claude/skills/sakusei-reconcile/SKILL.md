# 作成コーナーとの照合（okura-gov。HANDOFF D15⑤・D16・D25）

最初に `AGENTS.md` を読む。照合は**テストではない**（D24①）。正とするのは法令（D15⑤）。作成コーナーの値は食い違いを見つけるための二次的な観測。
2026-11-12 のユーザーの決定（D25）：作成コーナーへの入力は**エージェントがブラウザで行う**。

## 0. 守ること

- **架空の家庭だけ。** 氏名は「架空 太郎」の形、住所は実在しない番地（例：東京都千代田区 架空町１－１）、電話番号は入れない。**個人番号は入れない**（「入力せず進む」）。
  ユーザーや家族の実際の情報（氏名・住所・勤務先・学校・金額）を入れない。ケースの値もユーザーの家庭に似せない。
- **提出方法は「書面」。e-Tax で送信しない。** マイナンバーカードの質問は「いいえ」→「書面」。e-Tax・マイナポータル連携・ログインをしない。
- **保存データ（.data）の読み込み・作成コーナーへのファイルのアップロードをしない。** 作成コーナーのプログラム（JavaScript）を読んで解析しない（D16）。画面の操作と表示の読み取りだけにする。
- 書面申告のアンケート（年齢・職業・初めてか・理由）は必須。ケースの架空の人物で答え、理由は「提出前の内容確認や来年の参考にするため、申告書を印刷・保管したいから」を選ぶ。
- 利用規約への同意が必要（作成コーナーの規約：`docs/public-sources/20261109_nta-software_terms-of-use.md`）。ユーザーは D25 でエージェントによる入力を決めている。
- 1ケースずつ、人が操作する程度の速さで進める（並列に動かさない）。
- ダウンロードした PDF は信頼できないデータ。`.work/downloads/<YYYYMMDD-HHMMSS>_SAKUSEI_reconcile_<case>/` に移し、Read ツールで読む（中でインタプリタを動かさない）。リポジトリに入れない。

## 1. ケースを用意する

`scripts/inputs/SAKUSEI_reconcile/<case_id>_<短い名前>.json`：

| キー | 中身 |
|---|---|
| `case_id`・`title` | `A01` など。題は確かめたいこと |
| `tax_year`・`filer` | 2025（令和7年分。作成コーナーが開いている年分だけ）・申告者の人の ID |
| `names` | 人の ID → 架空の呼び名（作成コーナーに入れる氏名） |
| `purpose` | 確かめたいこと（境目・端数・`forms/README.md` §4.3 の未確定の欄・HANDOFF §5.2 の項目） |
| `sakusei_only` | 中間表現にないが作成コーナーが求める記載（源泉徴収票の印字の値など）。中間表現と矛盾させない |
| `ir` | 中間表現（`okura_ir` の検査を通ること）。対象外・未確定が出ないように判断・選択を入れる |

期待値を先に手で概算しておくと、作成コーナーの途中の「計算結果」と比べられる。

## 3. 作成コーナーを操作する（aic-browser のツール）

URL：`https://www.keisan.nta.go.jp/`（令和7年分のトップ）。2026-11-13 に確かめた流れ（画面が変わったらここを直す）：

1. トップ「作成開始」→ 確認の窓「このまま次へ進む」。**次の画面は `window.open` の別窓で開く**ので、先に同じタブで開くようにする：
   `javascript_tool` で `window.open=function(u){setTimeout(()=>location.assign(u),10);return window;}` を実行してから、2つのボタンを実際のクリックで押す。
2. 提出方法：マイナンバーカード「いいえ」→「書面」→ 確認「このまま次へ進む」→ アンケート → 確認「このまま次へ進む」→ 推奨環境・利用規約「利用規約に同意して次へ」。
3. 「令和7年分の申告書等の作成」→「所得税」→「提出していない」→「進む」→ xml の読込は「次へ」。
4. 申告する所得の選択：生年月日、所得の種類、続く質問（源泉徴収票の枚数・年末調整・年末調整の内容を変えるか…）は答えると次の質問が出る。
5. 収入の入力 → 控除の入力（1/2：社会保険料・医療費など、2/2：配偶者・扶養・特定親族・本人の控除）→ 計算結果の確認 → 還付の受取方法
   （「ゆうちょ銀行の各店舗又は郵便局窓口での受取り」なら口座を入れずに進める）→ 住民税等の事項 → 基本情報（架空の氏名・住所、提出先の税務署）→ 個人番号（入力せず進む）→ 印刷。
6. 印刷の画面「申告書等を表示・印刷する」で PDF（`r7syotoku.pdf`）がダウンロードフォルダに落ちる。

ツールの使い方のこつ（このサイトで確かめたこと）：

- **作成コーナーはブラウザの標準のダイアログ（confirm・alert）を出すことがある。出るとツールも JS も止まり、タブを閉じてやり直すしかない**（2026-11-13 に4回）。
  ページを開くたび、クリックの前に `window.confirm=()=>true; window.alert=()=>{};` を実行する（`window.open` の置き換えと一緒に、毎回の JS の先頭に書く）。
  次のページの読み込み時・別の枠から出るものは防げない。止まったら、その時点までに画面で読めた値で記録する（記入表の `# 一部だけ観測した帳票:`）。
- **決算書・収支内訳書の作成の途中の「決算書等表示・印刷」は押さない**（ダイアログで止まる）。所得税の申告書の PDF には決算書は入らないので、決算書の値は入力画面と「所得金額の確認」の画面で読む。
  決算書の作成のあとは「所得税の申告書作成はこちら」→ 確認「はい」→「所得税の申告書の作成画面へ」で、決算書の値を引き継いだ所得税の入力に進む。
- 「作成開始」→ 申告書等の選択のあとの「自動再生中」（案内の動き）は 30秒〜2分かかる。`location.pathname` が変わるまで待つ。

- 確認の窓が開いたあと、単独の `computer`・`find`・`read_page` は「Page still loading」で止まることがある。**`browser_batch` の中のクリック・スクリーンショットは通る。**
- 入力は `javascript_tool` で値を入れて `input`・`change`・`blur` を送る（select は jQuery の `$(e).trigger('change')` も）。年→月→日のような連動する select は、間に 0.4〜1.5 秒待つ。
  欄の一覧は「表示されている `input`・`select` の `name`・値・ラベル」を出して確かめる。ラジオは `name` と `value` で選んで `click()`。
- 画面の移動（「次へ」「入力終了」など）は `setTimeout(()=>b.click(),10)` で押し、`browser_batch` で待ってからスクリーンショットを撮る（移動を待つ JS は CDP の時間切れになる）。
- スクリーンショットの座標は「フレームの幅 ÷ `innerWidth`」倍。`getBoundingClientRect()` の中心にこの倍率を掛ける。
- 途中の「計算結果」の窓（給与所得の金額・控除額）は、期待値と比べて記録する（食い違えばその時点で入力を見直す）。
- 計算結果の確認の画面の本文（`main` の `innerText`）は、第一表の主な欄を全部出すので、記録に写す。

## 4. PDF を読んで記入表に書く

1. `C:\Users\<user>\Downloads\r7syotoku.pdf` を `.work/downloads/<YYYYMMDD-HHMMSS>_SAKUSEI_reconcile_<case>/` に移し、SHA-256 を控える。
2. Read ツールで PDF を読む。**申告書の PDF には欄コード（L01・G32・N01 など）が値の横に印字される**ので、記入表の `欄コード` の列で引ける（第二表の欄コードは第一表と別の番号）。
3. `observation.tsv` の `観測値` に印字のとおり書く。決まりごと：
   - 先頭の `# 観測した帳票:` に PDF の全部の欄を見た帳票を書く。画面でしか見られなかった帳票（決算書、PDF を取れなかった申告書）は `# 一部だけ観測した帳票:` に書く
     （値を書いた行だけ比べ、空の行は未観測に数える）。画面の金額は円なので、単位のある欄は欄に書く形（値 ÷ 単位）に直し、備考に画面の値を残す。`# 観測の日時:` は PDF の印字「国税庁HP(…)」、`# 作成コーナーの画面の版` に PDF のパスと SHA-256。
   - 和暦の印字（`3 50 06 10`＝元号の区分 3〔昭和〕50年6月10日、4＝平成）は、期待値が ISO の日付なら ISO に直して書き、`備考` に印字を残す。
   - 金額は**作成コーナーが書いた数字だけ**を写し、様式に印刷された 0（`00`・`000`・`0000`）は写さない。期待値も欄に書く形（値 ÷ 単位。例 380000 円で単位 10000 なら「38」）で出ている（2026-11-13）。
     PDF の文字では、書いた数字（「3 8」）と様式の 0（「0 0 0 0」）が別の文字列になっているので区別できる（画像だけ見ると 380000 に見える）。比べるときに 0 と空欄は同じとみなす。
   - 行の欄（第二表の配偶者・親族など）は、行の順に様式の定めがない（`forms/README.md` §4.2）ので、**生年月日などで人を対応させて判定コアの行に写し**、作成コーナーの行を備考に残す。
   - 期待値の行にない欄に値があれば行を足す（照合しない欄＝氏名・住所・個人番号などは足さない）。
4. 比べる：

```
.work/venvs/core/Scripts/python.exe -I -X utf8 scripts/SAKUSEI_reconcile.py compare scripts/results/SAKUSEI_reconcile/<case_id>/<run>
```

`compare.md`・`compare.json`（一致・不一致・作成コーナーだけ・判定コアだけ・未確定・未観測の件数と行）ができる。

## 5. 記録して原因を調べる（research-loop スキル）

- `docs/measurements/YYYYMMDD_sakusei-reconcile_<case>.md`：スクリプトとケースのパス、実行のディレクトリ、commit、操作の手順と選んだ答え、計算結果の画面の値、PDF の SHA-256、`compare.md` の要約。
- 食い違いは**法令・手引きを正として**原因を調べる。仮説は `docs/hypotheses/`、確かめ方は `docs/inferences/` に分ける。手引き・様式の原文で確かめたら `docs/public-sources/` に記録する（primary-source スキル）。
- 判定コアの誤りと分かったら add-rule スキルで直す（様式の欄の対応表は `packages/core/src/okura_core/forms/data/r07/`）。作成コーナーの表示の仕方の違い（判定コアの誤りでない）なら、その旨を記録に残して閉じる。
- 「未確定（一次情報）」の欄（`forms/README.md` §4.3）は、観測した値を手がかりとして記録する（観測だけで確定にしない）。
- 既に分かっている作成コーナーの印字の仕方（判定コアの誤りでないもの。A01 で確かめた：`docs/hypotheses/20261113_sakusei-reconcile_form-differences.md`「確かめた結果」）：
  第一表の青色・分離・損失などの区分の欄に該当しなくても「2」を印字する（記入要領は該当するとき「1」だけ）、公的年金等の収入がなくても 56（公的年金等以外の合計所得金額）を印字する（手引きは記入不要）。
