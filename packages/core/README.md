# okura_core：判定コア（版 0.2：規則モジュールの登録と所得税の概念の約束）

中間表現（`okura_ir`）と問いから、法令が決める値と判定を **根拠つき・決定的に** 出す純粋関数
`evaluate(中間表現, 問い, 注入データ) → 結果`（HANDOFF D7 改・D19・D21・D22、SCOPE §8）。
OpenFisca-Core 46.0.1 の上に、規則モジュール（`rules/<名前>/`）を組み合わせた法令パッケージで計算する。
`okura_ir` と `openfisca_core` に依存し、記録層（`okura_records`、beancount）は import しない（SCOPE §6-2）。

## 1. 責務

| する | しない |
|---|---|
| 中間表現・問い・注入データの検査（誤りは値を出さずに失敗で返す）。中間表現の項目の数の上限 | 台帳の読み込み・中間表現の作成（記録層） |
| 年分ごとの OpenFisca の situation の組み立て（R4 H6 提案2）。何をどう写すかは規則モジュールが宣言する | 見込みの作成、シナリオの選び方、最適化、助言（SCOPE §4・D19） |
| 値・状態・根拠・境目の説明・未確定の分かれ目・対象外の理由を出す | 様式の欄の対応表（別の部品。ここでは「申告用の値」を出すか止めるかまで） |
| 未入力の判断・選択と根拠のない端数を候補の全部で評価する（D21 R6・D22 S3・S20） | 候補の中から有利なものを選ぶこと（最適化しない：D22 S20） |
| 予測を含む申告者・年分から申告用の値を出さない規則を強制する（`result.build_filing`） | 市町村・保険者のデータそのもの（注入される。この版では包みの検査だけ） |

この版で計算するもの：**家族全員の所得税の令和7年分・令和8年分**（所得の種類ごとの所得 → 合計所得金額 → 扶養の割当てと人的控除・その他の所得控除
→ 課税所得 → 税額・源泉徴収税額の精算・申告の要否。規則モジュール kyuyo・income_kinds・income_totals・personal_deductions・other_deductions・tax）、
**住民税の令和8年度分・令和9年度分**（juminzei）、**国保料（税）の法令の構造**（kokuho）、**国民年金の保険料・免除等の所得基準と第3号被保険者**（kokunen）、
**健康保険・共済組合の被扶養者**（hifuyosha）と、その境目の説明。10 のモジュールは全部登録済み（`rules/__init__.py`）。
各モジュールの README の「実装していないもの」「対象外の一覧」は「対象外」として理由つきで返す（§6）。
（2026-11-11：版 0.2 の「給与所得だけ」の記述を結合のレビューで直し、Phase 3 の4つのモジュールが「未登録の雛形」という記述を共有の担当が直した。）
所得税の全概念（112）の名前・単位・期間・層・依存・担当は、規則モジュールの `concepts.yaml` に **約束** として置いた（§7.2）。

**Phase 3 の土台（2026-11-11）**：住民税・国保・国年・被扶養者を並行で実装するための共通の部分を足した。
問いの時点の窓口（`timepoints.py`：年度 F は所得の年分 F−1 の situation、判定日は判定日ごと。§5.2）、注入データのスキーマと検査

エンティティ `国保世帯`・`住民税扶養所属`、4つの規則モジュール（`rules/{juminzei,kokuho,kokunen,hifuyosha}/`。雛形の約束 53 件から始めて、全部が実装・登録済み。§7.2）。
共有の担当が足したもの（2026-11-11）：読んだときだけ開く判断・選択の1か所（§5）、境目の基準を概念の値で出す仕組み（§4）、モジュール間の窓口

## 2. 公開する関数とモジュール

```python
from okura_core import evaluate
from okura_core.result import dumps, check_result_json

res = evaluate(ir, query, injected=None)   # EvaluationResult か EvaluationFailure。例外は判定コアの誤りのときだけ
print(dumps(res))                          # 決定的な JSON（キーを並べ替え、時間・絶対パスなし）
assert check_result_json(res.to_dict()) == []   # schema/result.schema.json で検査（okura_ir の部分集合の検査器）
```

コマンド（標準入力 `{ir, query, injected}` → 標準出力の結果 JSON）：

```
.work/venvs/core/Scripts/python.exe -I -X utf8 -m okura_core.cli < input.json > result.json
```

終了コード：0 結果、2 入力の誤り（`{"ok": false, "errors": [{path, code, message}]}`）、3 判定コアの誤り（`internal_error`）、
4 起動のしかたの誤り（`-I` と `-X utf8` が要る。Windows の cp932 では日本語の YAML を読めない：R2 実測 T00）。

## 3. 入力

- `ir`：`okura_ir.validate` に通る中間表現（`packages/ir/README.md`）。項目の数の上限（`scope.py`。評価の時間を抑える仮の値で法令の値ではない）：
  人 2,000 人まで（`$.ir.persons`）、記録・判断・選択の合計 20,000 件まで（`$.ir`）。超えたら検査の前に `max_items` で失敗（シナリオの差分を足した後も同じ）。
- `query`：

```json
{"income_tax_years": [2025, 2026],
 "filing_date": {"on": "2027-03-10", "planned": true},
 "resident_tax_fiscal_years": [], "kokuho_fiscal_years": [], "kokunen_fiscal_years": [], "dependent_judgment_dates": [],
 "scenarios": [{"id": "s1", "label": "…", "judgments": [ …中間表現の判断… ], "choices": [ …選択… ]}]}
```

  任意のキー `workers`（2026-11-12）：候補の組を計算するプロセスの数（null・キーなしは CPU の数、1 は直列）。結果を変えない（§5.4 の5回目）。
  任意のキー `forms`（2026-11-12）：`{"persons": ["p-1"]}` か `{"persons": null}`（その年分に生存している全員）。様式の欄の値を、所得税の年分 × 申告者ごとに作る（§4）。
  `filing_date`・`kokunen_fiscal_years`（2026-11-11 に足した国民年金の年度）・`forms` 以外のキーは必須（空でも書く）。年は整数（bool・小数・文字列は誤り）。対象の年分の外は誤りではなく「対象外（年分外）」。
  シナリオは差分なしの `base` を先頭に足して全部評価する（`base` は予約語）。差分は判断・選択の追記だけで、足した後の中間表現を
  `okura_ir.validate` で検査し直す（誤りの場所は `$.query.scenarios[i].judgments[k]…`）。未入力の判断を埋めるシナリオは、未確定を決める材料になる。
- `injected`：`null` か配列。各項目 `{id, point, issuer{kind,code}, applies{from_on,to_on?}, source{url,retrieved_on,source_kind,title?,sha256?}, data{}}`。
  道府県（`prefecture`）の団体のコードは都道府県の団体コード（上2桁＋000＋検査数字。例 130001。誤りは `prefecture_code`。2026-11-12）。
  `point` は `injection_points.POINTS` の名前、`data` はその注入点のスキーマで検査する（知らない注入点・団体の種類の違い・数の欄の文字列・
  同じ注入点と団体の適用期間の重なりは誤り）。どの登録したモジュールも使わない注入点の項目は「対象外（未対応）」として返す（§5.3）。

| `scenarios[].filing` | 申告用の値 `entries` と、出さなかった値 `withheld`（理由と、止めた原因の値の ID） |

- **境目の基準**：概念の `境目` に、パラメータの葉1つ（`基準`。比較の向きはメタデータ）か、基準の額を値に持つ概念（`基準の概念` と `比較`。2026-11-11）を書く。
  基準の概念は、基準が判定日・年齢・制度などで変わり葉1つで書けないときに使う（例：`健保.年間収入が収入の基準額未満か` の境目 `健保.被扶養者の年間収入の基準`
  は `健保.収入の基準額` の値〔130万円・150万円・180万円〕と比べる）。根拠は基準の概念の値の根拠のうち同じ額のパラメータ（`evaluate.criterion_basis`）。
- **年齢の境目**（2026-11-12）：概念辞書の `年齢の境目`（`concepts/__init__.py` の docstring）に、比べる年齢（同じ制度の整数の出力）・判定の日
  （`その年12月31日`・`その年12月31日（死亡の時はその前日）`・`判定日`・`判定日の属する年の12月31日`）・基準（パラメータの葉。比較はメタデータ）か
  基準の年齢と比較（根拠は宣言した概念の定義）・除く条件（真偽の出力。真なら出さない）・判定日の下限（ISO の日付を値に持つパラメータの葉）を書く。
  evaluate は生年月日（中間表現の persons[].birth_on）と判定の日から年齢を求め（`result.age_at_end_of`・`attained_on`：誕生日の前日の終了時に加わる、
  2月29日生まれは平年の2月28日）、規則モジュールの年齢と同じ人だけに出す（違えば判定の日が別の日。比べる年齢が未確定・対象外の人も出さない）。
  年齢の比較だけを説明する（その比較が判定に効くかは related の値で見る）。宣言（2026-11-12）：personal_deductions の控除対象扶養親族（16歳）・
  特定扶養親族（19歳・23歳）・老人扶養親族（70歳）・同居老親等（70歳）・特定親族（19歳・23歳）・老人控除対象配偶者（70歳。配偶者その人の
  `所得税.扶養等の判定に使う年齢` に付けた）、判定する人の判定の時の値を使う人は除く。hifuyosha の `健保.収入の基準額` の60歳以上（判定日）・
  19歳以上・23歳未満（判定日の属する年の12月31日。判定日が 2025-10-01 より前なら出さない）。kokunen の第3号被保険者の20歳以上・60歳未満（判定日）。
  比べる年齢と除く条件のため、`所得税.扶養等の判定に使う年齢`・`所得税.判定する人の判定の時の値を使うか`・`健保.判定日の年齢`・
  `健保.判定日の属する年の12月31日の年齢`・`国年.判定日の年齢` に出力を足した（結果の値が増え、依存する値の depends_on・facts の形が変わる）。
- **状態**（D22 S2）：`見積り`・`計画`・`予測`・`未確定`・`対象外`。入力の記録・判断・選択の `mark` から入り、OpenFisca のトレースの依存に沿って
  依存する値へ伝わる（§6.2）。
- **未確定**（D21 R6）：`undetermined.splits[]`（分かれ目：ID・決める手段〔判断・一次情報など〕・対象・候補・結論を分けるか）と `outcomes[]`（候補の組ごとの値）。
  「何を入力すれば決まるか」は分かれ目の対象（判断の種類と人）で分かる。
- **根拠**：`type`（parameter・data・rounding・rule・injection）、`name`、`source_kind`、`references`（docs のファイル#節）、`flags`（法令の読み・原文未確認）、
  `law`、`value`、`instant`、`effective_from`、`enforced_on`、`detail`。
- **申告用の値**（D19・D21 R2）：人 × 年分ごとに、申告の範囲の値に `予測`・`未確定`・`対象外`、幅、施行日前の提出のどれかがあれば、その人・年分の全部を止める。
  `見積り`・`計画` は条件つきで出す。`FilingEntry` は `build_filing` でしか作れず、`ScenarioResult` も二重に確かめる。

## 5. 数値・端数・候補の評価（D21 R5・R6、D22 S3・S20）

- 金額は整数の円。途中の値は `Fraction`。float は受け付けない（`money.to_fraction`・`require_yen`）。OpenFisca の金額の変数は `int`（numpy.int32）で、
  int32 の上限を超える入力は OpenFisca に渡さず対象外にする（モジュールの入力の検出と `situation._check_value`）。
- 丸めは根拠のある箇所でだけ `rounding.RoundingRule`（名前・根拠の種類・出典・法令・読みの印）で行う。今あるのは
  `floor_yen_kyuyo_shotoku_660man_or_more`（別表第五 備考。確定申告への当てはめは法令の読み）。
- 決まらない入力（分かれ目）は2種類で、同じ道具（`candidates.py`）でまとめる：
  - 未入力の判断・選択（モジュールの `DecisionSpec` が宣言した1か所）：候補は中間表現の語彙の値の領域（真偽・列挙）か、宣言した候補。
    同じ1か所に食い違う判断があれば、違う値だけを候補にする。結論（値）が全部の候補で同じなら断定、違えば未確定（金額が違っても未確定）。
  - 根拠のない端数（モジュールの `RoundingSlotSpec`）：候補は切捨て・切上げ・四捨五入。候補の名前を入力変数で式に渡す。金額だけが違えば幅、
    判定が分かれたときだけ未確定（決める手段は一次情報）。式の外の純粋関数では `rounding.evaluate_unfounded` を使う（まとめ方は同じ）。
    金額かどうかは概念の値の型で決める（`円` だけ。`整数`〔人数など〕・真偽・区分は判定なので、端数で分かれたら未確定）。
  - 判断・選択と根拠のない端数の両方が金額を変えるときは、判断・選択の分かれ目だけで未確定にし、`outcomes` の値は端数の候補の幅にする
    （端数は何を入力しても決まらないので「何を入力すれば決まるか」に出さない。`evaluated` には出す）。
  - 法令の読みの候補（2026-11-12。D22 S1 の「支えが同程度なら両方で評価」に D22 S3 を当てる。モジュールの `ReadingSlotSpec(name, variable, title, candidates, explanations)`）：
    一次情報で決まらない読みの候補（2つ以上の名前。最初が既定の読み）を、根拠のない端数と同じ広げ方・まとめ方（方針 `Policy.READING`）で評価する。
    金額だけが違えば幅、判定が分かれたときだけ未確定（決める手段は一次情報）。分かれ目の ID は `読み:<name>`、対象に `title` と候補の説明。
    `variable`（文字列の入力変数）に候補の名前が入り、式は読みで値が違う人がいるときだけ引く（引いたときだけ開く）。`variable=None` なら `ctx.reading(name)` で読む。
    使っている箇所：juminzei `読み:住民税の課税標準の千円未満の切捨ての当て先`（JM-22）。
    以前からの「読みの分かれ目を入力の missing に付ける」形（other_deductions の `facts.reading_split`、income_kinds の IK-01・98、juminzei の separate.py など）は、
    金額でも未確定（`outcomes` は空）になる。金額だけが違う読みは `ReadingSlotSpec` に移せば幅で返る（各モジュールの担当への申し送り。候補ごとに式で値を出せる読みに限る）。
- 読んだときだけ開く判断・選択の1か所（2026-11-11。`DecisionSlot(lazy=True)`）：分かれ目になるかが段の値（所得など）で決まる1か所は、
  宣言の時（段の前）には要るか分からない。lazy な未入力の1か所は最初は直積に入れず最初の候補で計算し、`build_inputs`・段の関数が
  `ctx.decision` で読んだ候補の組があったときだけ分かれ目として開き、評価し直す（根拠のない端数の `RoundingSlotSpec(variable=None)` と同じ広げ方。
  `YearWindow.lazy_decisions`・`decision_reads`、`situation.Decisions.lazy`）。読まれなければ結果の分かれ目にも出ない。単調な判断の群にはできない。
  使っている1か所：`選択.扶養の所属`（personal_deductions。所令219②二の同額のときだけ段が読む。反証のレビューの指摘）。
- 単調な判断の両端評価（D21 R6）：支出ごとに分かれ目があって直積が爆発する判断は、`DecisionSlot(monotone=群の名前)` と宣言すれば、同じ群の未入力の1か所を
  両端（全部 候補0・全部 候補1）だけで評価する（モジュールは値が群の各1か所について同じ向きに単調であることを保証する。方針 `Policy.MONOTONE`）。
  結論が同じなら断定、金額は幅、判定が分かれたら未確定。分かれ目の ID は `単調:<群>`、対象に1か所ごとの `members`。入力された1か所は群から外れて固定する。
- 根拠のない端数の分かれ目は、式がその候補の入力変数を実際に引いたときだけ直積に入れる（2026-11-11 の結合のレビュー。端数の出ない評価では、どの候補でも値が同じなので
  候補を評価しない。候補を引いた分かれ目を足して、新しく引かれるものがなくなるまで広げる）。式は、端数が出る人がいるときだけ候補を引く形に書く。
  `RoundingSlotSpec(variable=None)` の端数は、`ctx.rounding_candidate`・`ctx.round_unfounded` で読んだときだけ開く（段階の関数の読みを含む）。
- **値ごとの候補の評価**（2026-11-12 の4回目。`evaluate._resolve_dependencies`。以前は人のつながりごとに直積を取り、上限を超えたら分かれ目を1つずつ
  動かして関係する値を決める近似〔`_affected_inputs`〕で、2つ以上の分かれ目が同時に変わったときだけ変わる値を見落としうった）：値ごとに、
  その値が依存する分かれ目 D を計算の過程から決め、D の候補の直積の全部の組を評価する（ほかの分かれ目は最初の候補。関係のない分かれ目の
  組合せは計算しない）。D のどの組でも D の外の分かれ目に依存しなくなるまで D を広げる。
  - 入力・対象外・グループのインスタンスが依存する分かれ目：それを作った作り手（build_inputs・グループの組み立て・段の関数）が読んだ
    1か所（`YearBuild._reads`・`StageState.reads`）。build_inputs とグループの組み立ては、読んだ分かれ目の直積が `PRODUCER_ASSIGNMENTS`
    （1024）以内なら直積の全部の組で呼んで、出力ごとに正確に決める（`_producer_dependencies`。Python の関数だけで、OpenFisca は計算しない）。
    超えたら安全側：出力を書いた時点までに読んだ1か所（`registry.CAPTURE` の因果）のうち、関係する人（`Slot.persons`）にその人を含む
    分かれ目か人に結びつかない分かれ目。段の関数の出力は段が読んだ全部の分かれ目。端数の候補を渡す入力はその端数の分かれ目。
    **2026-11-13（B1 の直し）**：build_inputs の直積が上限を超えたら、安全側にする前に、人ごとに決める（`_producer_dependencies_by_person`）：
    人 q の出力は、関係する人に q を含む分かれ目と人に結びつかない分かれ目だけの直積の全部の組で作り手を呼んで、出力ごとに正確に決める
    （ほかの分かれ目は組のまま。安全側の決め方と同じ「関係する人」の宣言の約束に拠る）。人ごとの直積の合計も上限を超えたら、前と同じ安全側。
    市町村・道府県の注入データの1か所には、その団体の注入データを引く人を宣言する（`rules/juminzei/inputs.municipal_slots`）。
  - 値が依存する分かれ目：トレースで推移的に依存した入力（`_Raw.inputs`）と、集め忘れの検出が見る値の入力（`_Raw.extra`）が依存する
    分かれ目。**2026-11-13（B1 の直し）**：人をまたぐ値の入力は、(1) 人をまたぐ辺を通った先で引いた変数だけを、つながった人の全部について
    数え、それ以外の変数は値の人についてだけ数える（`_Closure.crossed`・`readers`）。(2) グループの組み立ては、値の概念が宣言したグループ
    だけを数える（`attached_groups`。以前は人をまたぐ値に全部のグループ：所得税の値が住民税の扶養の割当て・健康保険・国保の世帯のグループを
    通して、ほかの制度の注入点に依存したことになっていた）。計算の後の検出（`checks`）が対象外にしうる変数（検出のコードに名前を書いた検出のモジュールの変数と、どこかで対象外にした変数：
    `_check_target_candidates`）に依存する値は、その検出が読んだ値の入力が依存する分かれ目にも依存する。
  - 確かめ：評価した2つの組で1つの分かれ目だけが違うのに入力・対象外・グループが変わったら、その入力をその分かれ目に結びつける
    （人の宣言の約束が破れていても、評価した組の中では見落とさない）。
  - D の直積が `candidates.MAX_ASSIGNMENTS`（64。仮の値）を超えた値は計算せず未確定（D の分かれ目に「評価しなかった理由」、`outcomes` は空。
    注入されていない注入点にも依存するなら、その分かれ目を前に並べる）。値・状態・根拠は基準の組（全部が最初の候補）のもの。
  - 値ごとに、D のうち値の入力を変える分かれ目（`evaluated` に出す。グループはその人のインスタンスが変わるとき）だけで候補をまとめる。
- 所得税の年分の単位と同じ年の判定日の単位は、窓口を合わせた1つの situation で1回だけ評価し、単位ごとの値の ID（`Unit.tag`）で返す
  （`evaluate._shared_units`。2026-11-12 の4回目。判定日の単位が所得税の全部の値と段階評価をもう一度計算していた）。

### 5.2 問いの時点と評価の単位（timepoints.py。2026-11-11）

### 5.1 段階評価（D23 K1、SCOPE §6-3）

全員の所得をまず計算し（第1段）、規則モジュールが宣言した **段階の間の純粋関数**（`StageSpec`）で人をまたぐ関係を決め（第1段の値と関係から）、その結果を入力に入れて再び計算する（第2段）。

- 段は宣言で何段でも足せる。順序は `StageSpec.reads` の変数の依存（概念辞書の宣言と「集める先」）から決まり（`registry._plan_stages`）、読む変数がほかの段の `writes`・`groups` に依存する段は後ろへ回る。
  循環は登録の時点で `stage_cycle` として止める。段の書く入力変数は事実の層に置き、概念に `段階: <段の名前>` を書く（SCOPE §6-3「概念辞書に記録する」。登録の時点で確かめる）。
- 候補の組ごとに段を計算し直す（段の値が候補で変わる分かれ目は、最後の計算の入力の違いとして `_diff_builds` が捉える）。中間の回では段が読む値と、集め忘れの検出が見る値だけを計算し、まだ計算していない段の出力に依存する変数を読む
  計算の後の検出（`checks`）はその回では飛ばす。**段の読んだ値は最後の計算でも同じこと**を確かめ、違えば `ValueError`（段の依存の宣言の誤り）。
- 由来の伝搬：段の出力（`StageOutput.set`・`group` の `uses`）に読んだ値（`StageValue`）を渡すと、その状態（予測など）・対象外の理由・事実の ID・依存の値の ID・根拠が、段の出力の入力に依存する値へ伝わる。`uses` を渡さなければその段で読んだ値の全部を使ったものとする（安全側）。
  段の根拠は `StageSpec.basis`（段のすべての出力）と `set(..., basis=...)`。出力の変数を書く段では根拠・事実は段の出力の値に付き、依存する値には `depends_on` で見える（§4）。
- 関数を持たない段（`StageSpec(run=None)`）は値だけを読んで `build_inputs` に渡す（`ctx.stage_value(段の名前, 変数, 人)`。最初の段では `pending` の値）。このとき `writes` は `build_inputs` が書く入力変数を宣言する。
- 後の段の出力を読む段（`StageSpec.late_reads`。2026-11-12。kyuyo KY-10）：順序の決定に使わない変数を `ctx.late(変数, 人)` で読む。最初は `pending` の値（既定値）。
  evaluate は全部の段と最後の計算の後に、段が late で読んだ値を最後の計算の値と比べ、違えば最後の計算の値を渡して段階評価をやり直す（不動点の繰り返し。
  `registry.MAX_FIXPOINT`＝6 回。収束しなければ pending の値でもう一度計算し、段は pending のときの安全側の扱い〔対象外など〕をする。`evaluate.converge`）。
  late で何も読まなければ繰り返さない（読んだ人だけが繰り返しの原因になる）。人ごとに順序が決まる人をまたぐ判定（変数の単位では循環する）に使う。

### 6.2 状態の伝搬（D19・D21 R2）

  どの人を通ったかはトレースに残らない）。**2026-11-13 に改めた（B1 の直し）**：つながった人の全部について伝えるのは、人をまたぐ辺を
  通った先で引いた変数（`_Closure.crossed`）だけにした。人をまたぐ辺を通らずに引いた変数（本人の住所地の市町村の級地など）は、値の人の
  分だけを伝える（式は人ごとの計算で、ほかの人の値を読むのは人をまたぐ読み方だけ。同じ変数を両方の道で引くなら、つながった人の全部）。OpenFisca では人をまたぐ依存はグループの中でしか起こらないので、つながっていない人からは伝えない。
  人の変数が人の変数を引く `人.法律婚.members("…")`・`人.法律婚.sum(人("…"))` はトレースに同じ人の依存と同じ形でしか残らないので、
  宣言で判定する（宣言は構造の検査が AST で求める。2026-11-11 のレビュー：以前は人でないエンティティの変数を通ったときしか人をまたぐと
  判定せず、配偶者の予測の給与に依存する値に `予測` が付かなかった）。
- ただし、値の変数そのもの（例：申告者の `所得税_扶養控除の額`）については、その人の対象外だけを見る。OpenFisca では同じ変数・同じ期間を式の中で引けないので、
  つながったほかの人の同じ名前の変数の対象外は、この値に依存しない（2026-11-11 の結合のレビュー：国外居住親族自身の所得控除の額を「範囲外」にすると、
  扶養所属のグループを通して申告者の同じ名前の控除の額まで対象外になっていた）。トレースでたどった変数は、引き続きつながった人の全部を見る。
- グループの組み立ての由来（`GroupInstance.record_ids`・`states`：印つきの婚姻の記録など）は、その人が入るインスタンスについて、
  グループを使う値（人をまたぐ依存か、宣言した依存をたどってグループの概念〔`所得税.扶養の割当て`・`所得税.法律婚`〕に届く値）に付ける。
  **2026-11-13 に改めた（B1 の直し）**：人をまたぐ値でも、付けるのは宣言した依存をたどって届くグループだけ（`evaluate.attached_groups`）。
  以前は人をまたぐ値に全部の種類のグループの由来を付けていたので、所得税の値（ひとり親・扶養親族など）に、住民税の扶養の割当て・健康保険・
  国保の世帯のグループの由来（状態・事実・根拠・対象外）が伝わっていた。人をまたぐのに宣言したグループが1つもない値だけ、前と同じ全部。
  役割だけを使う式（`人.has_role(扶養所属.申告者)`・`人.法律婚.nb_persons()`）も、グループの概念を `依存する概念` に書く（構造の検査）。
- 段階の間で読んだ値の状態・対象外・根拠は、段の出力の入力（`InputValue.uses`）・グループ（`GroupInstance.uses`）を通して依存する値へ伝わる（§5.1）。
- 以前は、判断・選択を持つ人の合計所得金額を対象外にして止めていた（予測の伝搬の代わり）。今は、使う判断は状態として伝え、使わない判断は所得に関係しうる種類だけ止める。

## 7. 名前の規則・層・概念辞書

### 7.1 名前

- OpenFisca の変数：`<制度>_<日本語の名前>`（制度の接頭辞は 所得税_・住民税_・健保_・国保_・年金_）。概念 ID：`<制度>.<名前>`。
  新しい概念の変数名は、概念 ID の `.` を `_` にしたもの（例 `所得税.事業所得の金額` → `所得税_事業所得の金額`）。
- エンティティは `人物`（人）・`扶養所属`（申告者〔最初・max1〕／扶養親族等）・`法律婚`（配偶者 max2）・`健康保険`（対象外〔最初〕／被保険者 max1／被扶養者）。
  situation は全員を全部のグループに明示して書く（組み立てるモジュールがないグループは自分だけのインスタンスの最初の役割）。
- パラメータ：`rules/<名前>/parameters/<制度>/<…>.yaml`。名前は `所得税.給与所得.措法第29条の4第2項.第2号.控除額` のような日本語の木。
  日付のキーは **適用開始日**（所得税は年分の1月1日）。値ごとの `metadata`：`law`、`source_kind`、`reference`（docs のファイル#節）、`施行日`、`flags`、
  `reading`、`比較`、`適用`、`law_revision`、`unit`。率は `率.分子`・`率.分母` の整数。YAML はコードとして扱い、タグを書かない。
  モジュールの木は build_system が1つに合わせる。同じ葉を2つのモジュールに置くと誤り。

### 7.2 層と概念辞書

## 10. 規則モジュールの足し方

規則は `rules/<名前>/` のディレクトリだけで足す。**共有のファイル（`evaluate.py`・`situation.py`・`registry.py`・`country/__init__.py`・
`concepts/structure.yaml` などの共通の部分）は触らない**。触る必要があると思ったら、並行の担当と調整してから。

```
rules/<名前>/
  __init__.py      MODULE = RuleModule(...)（未登録の雛形は空）
  README.md        作る概念・上流の概念・注意
  concepts.yaml    概念辞書の項目（制度・担当・既定・概念）。約束の名前・単位・期間・層を変えない
  variables.py     OpenFisca の Variable（任意の名前のファイルでよい）
  parameters/      OpenFisca の YAML（<制度>/<…>.yaml。日付のキーは適用開始日、metadata 必須）
  data/            大きな表（CSV と SOURCES.json）
```

手順：

1. 一次情報（docs/public-sources・docs/measurements）で条文・基準額・施行日を確かめる。記憶で値を書かない（AGENTS.md）。
2. `concepts.yaml`：実装する概念を `実装済み: true` にし、`未実装のとき` を消す。依存する概念・パラメータ・制度／人／年をまたぐ依存・
   集約点を通らない依存を根拠つきで宣言する（宣言のない依存は構造の検査で止まる）。新しい概念を足してよい（ID・変数名を約束の形で）。
3. `parameters/`・`data/` を置く（出典・根拠の種類・適用開始日・law）。
4. 変数を書く。式は同じ層か下の層の変数だけを引く。まだない上流の概念は、約束の変数名で引けば仮置きの変数が受ける
   （評価では、その値が0とみなせない人は対象外になる）。テストでは `SimulationBuilder().build_from_entities(build_system(), {...})` で
   仮置きの変数に値を与えて単独で確かめる。
5. `__init__.py` に `MODULE = RuleModule(...)`：

| 項目 | 書くもの |
|---|---|
| `name`・`title`・`directory` | ディレクトリの名前・表題・`Path(__file__).resolve().parent` |
| `variables` | 変数のクラス |
| `record_kinds` | 使う中間表現の記録の種類（ここに書いた種類は「使わない記録」の対象外の項目から外れる。実装していない種類は書かない）。種類より細かく書くなら `RecordKind("filed_document", "document_type", frozenset({"final_return", …}))`（`attributes` の欄の値で絞る。書類の種別ごと） |
| `build_inputs(ctx) → ModuleInputs` | 入力変数の値を、`ctx.persons`（その年分に生存している人）の全員について `out.set(変数, 人, 値, 記録の ID, 状態)`。対象外は `out.exclude(人, 理由, 変数)`（変数なしなら人の全部） |
| `injections` | `InjectionSpec(注入点, slots)`：`slots(ctx)` が `InjectionSlot(key, 団体の種類, 団体のコード, on, target={}, candidates=None, persons=None)` を返す（key の既定の形は `injection_key(…)`）。値は `ctx.injection(注入点, key)`（§5.3） |
| `decisions` | `DecisionSpec(kind, slots)`：`slots(ctx)` がその年分に要る `DecisionSlot(key, target, matches, candidates=None, year_filter=True, persons=None, monotone=None)` を返す（`year_filter=False` は、その年分と重ならない判断も見る：前年の受診日の生計など。`persons` は関係する人〔省略は `target` から導く〕、`monotone` は単調な判断の両端評価の群の名前：§5）。値は `ctx.decision(kind, key)`（`Decided`。`open` なら候補の値）。由来（`record_ids`・`states`）を入力に入れる |
| `readings` | `ReadingSlotSpec(name, variable, title, candidates, explanations={})`：法令の読みの候補（§5。金額なら幅）。`variable` は文字列の入力変数（このモジュールの変数）か None（`ctx.reading(name)`）。端数と同じく、式は読みで値が違う人がいるときだけ引く |
| `roundings` | `RoundingSlotSpec(name, variable, title)`：根拠のない端数。`variable`（文字列の入力変数）に候補の名前が入るので、式で `rounding.FUNCTIONS[名前]` を使う。**式は端数が出る人がいるときだけ候補を引く**（引いたときだけ分かれ目を開く：§5）。入力の段で丸めるなら `variable=None` にして `ctx.rounding_candidate(名前)`・`ctx.round_unfounded(名前, 値)` を使う（読んだときだけ開く） |
| `groups` | `{"扶養所属一覧": builder}`：`builder(ctx)` が `GroupInstance` を返す（生存している全員がちょうど1回。グループを組み立てるモジュールは1つだけ） |
| `stages` | `StageSpec(name, title, reads, writes, groups, run, after, basis)`：段階評価の段（§5.1）。`run(ctx: StageContext) → StageOutput`。`reads` の変数を `ctx.value(変数, 人)`（ほかの人の値も）で読み、`out.set(変数, 人, 値, 記録の ID, 状態, uses=[読んだ値], basis=[…])`・`out.group(名前, インスタンス)`・`out.exclude(…)`。`writes` の変数（事実の層の入力変数）の概念に `段階: <name>` を書く。読む変数の依存から順序が決まり、循環は登録の時点で止まる |
| `checks` | `check(CheckContext) → Exclusion`：計算の後の対象外の検出（`ctx.calc(変数)`、`ctx.parameters`、`ctx.filing_date`）。段階評価の中間の回では、まだ計算していない段の出力に依存する値を読む検出は飛ばす |
| `rules`・`rules_by_year`・`basis` | 変数 → パラメータでない規則の根拠（`BasisEntry`）、年分別の根拠 `{年: {変数: 根拠}}`、変数 → 根拠を自分で組み立てる関数（税率表など、トレースに残らない規則） |

`build_inputs` と段の関数の窓口（`YearContext`、段の関数は `StageContext` で同じものが使える）：

| 窓口 | 使い方 |
|---|---|
| `ctx.relations` | 人をまたぐ関係（`relations.RelationView`）：`of(人, 種類, on=/overlaps=)`・`between(a, b, …)`・`spouses(人, 日)`・`parents`・`children`・`kin(人, 日)`（親子・養子縁組・婚姻・里親委託をたどった人とたどり方。親族の範囲の判定はモジュール）・`judgments(種類, 人, 相手, on=)`（判断の記録）。1人が複数の人の扶養親族に当たりうる「有する」のような関係は、グループではなくこの窓口で引く。区間はどの関係にも付く（`Relation.from_on`・`to_on`・`active_on`） |
| `ctx.value(変数, 人)` | （段の関数）前の段のほかの人の値（`StageValue`。`value`・`states`・`facts`・`reasons`・`basis`）。出力の `uses` に渡す |
| `ctx.stage_value(段の名前, 変数, 人)` | （`build_inputs`）`StageSpec(run=None)` の段の読んだ値。まだ計算していない段では `pending=True` の既定値（`value` は変数の既定値）。`out.set(…, uses=[v])` |
| `ctx.parameters`・`ctx.parameters_at(日)`・`ctx.parameter_root`・`ctx.parameter_basis(名前, on=None)` | パラメータの窓口（`parameters` はその年分の1月1日、`parameters_at` は施行日をまたぐ版の切替えに）。`parameter_basis` は `out.set(…, basis=[…])` に入れる根拠 |
| `ctx.rounding_candidate(名前)`・`ctx.round_unfounded(名前, 値)` | 根拠のない端数の候補（`RoundingSlotSpec.name`）。読むと分かれ目を開く |
| `ctx.windows`・`ctx.window(制度, 問い)` | この situation が答える問いの時点（`timepoints.Window`。§5.2）。所得税の年分だけの situation では住民税などの窓口は `None` |
| `ctx.injection(注入点, key)`・`ctx.injected` | 注入データの1か所の値（`Decided`：`value`・`record_ids`・`basis`・`missing`）と、注入データの全体（§5.3） |
| `ctx.filing_date` | 問いの提出日（予定日）（`query.FilingDate`：`on`・`planned`。D22 S4。`CheckContext`・`BasisContext` にもある）。問いになければ `None` |

5a. 年度・判定日の値を出すモジュールは `ctx.window(制度, 問い)` で時点を引き（§5.2）、市町村・保険者のデータは `injections` で宣言して
   `ctx.injection` で引く（§5.3）。所得税の値は同じ期間の変数を引き、概念辞書の「制度をまたぐ依存」に書く（年をまたぐ依存にしない）。
6. 登録していなければ `rules/__init__.py` に1行 `from .<名前> import MODULE as <名前>` を足す（並びは結果の順にだけ効く）。
7. テストを `packages/core/tests/test_<名前>*.py` に足し、全部のテスト（特に `test_architecture*.py`）を通す。境目は年分ごとの境目のテスト（D15 ②）、期待値に出典。

並行の担当への約束：

- 他のモジュールのディレクトリのファイルを直さない。ほかのモジュールの概念の名前・単位・期間・層を変えたいときは、その担当と合わせる。
- 同じ判断・選択の1か所を複数のモジュールが使うときは、同じ `kind` と `key` にする（同じ分かれ目として1回だけ評価される）。
  `判断.生計を一にする` の key は `"<subject.person>:<subject.other_person>"`。
- 人をまたぐ関係を決める段（§5.1）は `stages` に宣言する。段の入力は `uses` に読んだ値を渡し（渡さなければ読んだ値の全部）、書いた変数の概念に `段階: <段の名前>` を書く。ほかの人の値を式の中で引かなくても、段で値を決められる。
- 判断の分かれ目が多いときは、`DecisionSlot.monotone`（§5）や `persons` を宣言すると直積が小さくなる。`income_kinds` の「判断がなければ全額を必要経費」の読みは、業務関連性の判断の1か所を `monotone="業務関連性:<人>"` にして置き換えられる（全部 true・全部 false の両端の幅になる）。
- グループの組み方を使う式は、そのグループの概念（`所得税.扶養の割当て`・`所得税.法律婚`）を `依存する概念` に書く。ほかの人の値を
  引く式は `人をまたぐ依存` に書く（`人.法律婚.sum(人("…", period))` のように集約に渡す配列も）。どちらも構造の検査が AST で求め、
  evaluate はこの宣言で状態・対象外を伝える。式でほかの年分の値を引かない（evaluate は対象外にする。前年以前の記載はその年分の入力にする）。
- 集約点（合計所得金額・総所得金額・総所得金額等・所得控除の合計など）に集める概念は、自分の概念の `集める先` に集約点を書く。
  集約点の担当が依存する概念に足して式で引くまでは、その概念が0と言えない人の集約点の値は対象外になる（集め忘れを黙って通さない）。
- 同じ記録の種類を複数のモジュールが使ってよい（例：`salary_payment` は kyuyo の収入金額、tax の源泉徴収税額、other_deductions の社会保険料）。
