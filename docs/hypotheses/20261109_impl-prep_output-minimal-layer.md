## H1：出力層の最小の形は「申告書の欄ごとの値と根拠の一覧」（以下「欄値表」）。e-Tax の XML は最小の形に含めない

- 内容：判定コアの結果を、申告書の欄に対応づけた一覧にして出す。1行＝1つの欄。列は次のとおり。

| 列 | 例 | 意味 |
|---|---|---|
| 年分 | 2025 | 令和7年分 |
| 申告者 | 役割（親、子） | 中間表現の役割（D5） |
| 書類・様式ID | `NTA1K?A020010230`（第一表。`?` は数字の 0 か英字の O か未確定［PS §5.1］） | 紙の様式の様式ID |
| 欄番号 | ㉓ | 様式に印字された丸数字 |
| 欄コード | `G58` | 新様式に印字されたコード |
| 欄名 | 扶養 | 様式の文言 |
| 値 | 630000 | 円（整数）。区分欄はコード値（例 `G109`＝人数）。（例の金額は形を示すための架空の値で、基準額の主張ではない。2026-11-09 独立検証で注記） |
| 単位の制約 | 0000 | 様式に印字された 0 の数（1万円単位など） |
| 根拠 | 基準額の出典、使った事実の取引ID、法令パッケージの版、端数処理関数の名前 | D13 |
| 記入の注記 | 「特親欄は万円単位」など | 様式・記入要領の文言 |

- 根拠：
  - 申告書の欄は公開の様式で決まっていて、令和8年9月以降の新様式には欄ごとのコード（`G58` など）と様式ID が印字されている［PS §1、§2.2、§2.3］。欄値表は、紙に手で書く場合にも、作成コーナーで作った申告書と欄ごとに突き合わせる場合（D15⑤）にも、同じ鍵で使える。
  - 作成コーナーは、外で作った申告書のデータを取り込む入口を持っていない。取り込めるのは医療費集計フォーム、医療費通知の XML、作成コーナー自身が保存した `.data`、決算書・収支内訳書の `.xtx`（e-Tax 送信時の添付）などで、`.data` の形式は公開されていない［PS §6.1］。
  - e-Tax の XML（`.xtx`）を作れば e-Taxソフト（WEB版）の「作成済みデータの利用」で読み込んで送信できる［PS §7.3］。しかし、(1) e-Tax・e-Taxソフト（WEB版）を使うとユーザーは e-Tax の利用規約の「システム利用者」になり、第4条（リバースエンジニアリング禁止など）が適用される［PS §8.3、TOU §3］。e-Tax の「システム利用者」に当たらないという前提［SC 冒頭］と、作成コーナーの解析の判断の前提が変わる。(2) 仕様書は CAB 形式で、標準ライブラリで展開できない［PS §7.2、M §5］。(3) 帳票のバージョンが年ごとに上がり（所得税の KOA020 は令和9年1月受付で 24.0）、令和8年分の確定版の仕様は 2026-11-25 掲載予定［PS §5.3、§7.2］。
- 反証の条件：ユーザーが e-Tax で申告することに決めた場合（そのときは H8 に進む）。作成コーナーに外部のデータを取り込む公開の入口が見つかった場合。
- 確かめ方：推測 `docs/inferences/20261109_impl-prep_output-checks.md` の I4。

## H2：欄値表とは別に「作成コーナーに入力する値の一覧」（以下「入力値表」）を出す

- 内容：作成コーナーの画面では、申告書の欄の値ではなく、その元になる値（給与の支払金額・源泉徴収税額・社会保険料などの源泉徴収票の値、事業・業務の収入と経費、医療費、親族の氏名・生年月日・所得）を入れ、計算は作成コーナーのサーバーが行う［SC §5］。そこで、中間表現の事実のうち作成コーナーに入れるものを、申告者ごとに並べて出す。作成コーナーの計算結果（印刷した申告書）は、欄値表と欄コードで突き合わせる（D15⑤）。
- 根拠：作成コーナーの計算はサーバー側［SC §5］。医療費の入力方法は7通りあり、ファイルで取り込めるのは医療費集計フォームだけ（XML はマイナポータル連携か保険者のデータ）［PS §6.1］。
- 限界：作成コーナーの入力画面の項目は、e-Tax FAQ の画面写しで医療費の部分を見ただけで、所得や他の控除の画面は見ていない［M §6］。入力値表の項目名は、ユーザーが作成コーナーを使うときに合わせて直す必要がある。

## H3：医療費は「明細書の行」と「医療費集計フォーム（Ver.3.1）互換の xlsx」を出す。代わりの経路として「合計額 A・B」も出す

- 内容：
  1. 明細書の行：申告者（＝支払った人）ごとに、受診者×支払先でまとめた行（受診者の氏名、支払先の名称、医療費の区分の4つの印、支払った医療費の額、うち補塡される金額）。医療費通知を使う分は、明細書の「1 医療費通知に記載された事項」の (1)〜(3) として別に合計する。
  2. 医療費集計フォーム互換の xlsx：上の行を、B〜J 列・9〜1003 行に入れる。制約：1ファイル＝1申告者、最大 995 行、B は全角10文字以内、C は全角20文字以内、D〜G は「該当する」か空、H・I は半角数字9桁以内の整数、J は任意。
  3. 合計額：明細書の A（支払った医療費）と B（補塡される金額）。作成コーナーの「既に明細書を作成している」→「合計額の入力」に使い、明細書（1. を印刷したもの）は書面で別に提出する。
- 根拠：明細書の記載事項は、医療費の額・診療等を受けた者の氏名・病院等の名称・その他参考となるべき事項（所得税法施行規則第47条の2第12項）［PS §3］。様式は受診者・支払先ごとにまとめて書ける［PS §4.2］。医療費集計フォームの列と制約［PS §6.2、M §3.3］。合計額だけ入力する経路と「明細書は e-Tax で送信されないので別途提出」の注記［PS §6.1］。医療費集計フォームに支払者の列はない［PS §6.2］ので、中間表現の「支払った人」（D5）でファイルを分ける。
- 限界：
  - 補塡される金額は「その給付の目的となった医療費の金額を限度」とし、他の医療費からは引かない［PS §6.2］。1つの給付が複数の行に関わる場合の行への割り振りは、医療費控除のトピック（判定コア）で決める。出力層は行ごとに I ≦ H になっていることだけを検査する。
  - 作成コーナーは「推奨環境を満たさない表計算ソフトで作成した医療費集計フォームは読み込みができない場合があります」としている［PS §6.2］。プログラムで作ったファイルが読めるかは分からない（推測 I2）。
  - セルフメディケーション税制には医療費集計フォームを使えない［PS §6.2］。

## H4：欄の鍵は「年分 × 様式ID × 欄コード」とし、欄番号・欄名を必ず併記する。対応表は年分ごとに持つ

- 内容：欄値表の欄の定義（欄番号・欄コード・欄名・単位の制約・記入の注記）を、年分と様式ID ごとの表としてデータで持つ（判定コアのパラメータとは別。D2・D9 の「影響する層」の「出力の整形」に当たる）。令和7年分は §2 の一覧から作る。令和8年分は様式が公表されてから作る。
- 根拠：欄コードは令和8年9月の国税システムの更改で初めて印字された［PS §1］。e-Tax の KOA020 は令和9年1月受付でバージョンが上がる［PS §5.3］。令和8年分には社会保険料控除等の明細書（KOB500）が加わり［PS §3、§5.3］、施行規則第47条第3項第二十四号に記載事項（措法第41条の15の5 の扶養親族）がある［PS §3］（独立検証での補足：この号は 2026-01-01 施行の版から入っていて、措法第41条の15の5 は令和8年分・令和9年分の特例。令和7年分の様式にない記載事項が令和8年分で要る可能性がある［PS §3、MV V3］）。令和8年分の様式は 2026-11-09 時点で未公表［PS §2.6］。欄コードは画像からの転記で誤りがありうる［M §3.1］。
- 注記（2026-11-09 独立検証）：第一表・第二表・医療費控除の明細書の様式ID は `K` の次の文字が数字の 0 か英字の O か確定していない［PS §5.1、MV V2］。鍵に使う前に確定させる（H10）。欄コード（第一表・第二表）は独立検証で画像と全部突き合わせて一致した［MV §3「確かめたもの」］。
- 確かめ方：推測 I1。

## H5：欄値表は「単位の制約」を検査する。端数処理は判定コアの名前つき関数が行い、出力層はやり直さない

- 内容：様式に「0000」と印字された欄（⑰・⑱、⑲・⑳、㉑・㉒、㉓、㉔、㉕）は 1万円の倍数、「000」の欄（㉛、66）は 1,000円の倍数、「00」の欄（㉟、㊱〜㊳、52、55、65）は 100円の倍数であることを、出力の時に検査する。合わなければ出力を止めて「判定コアと様式の食い違い」として報告する。㉛の千円未満切捨て、㊺の1円未満切捨て、㊿・52の100円未満切捨て（手引きの記載）は判定コアの端数処理関数（D13）で行い、欄値表の根拠に関数名を書く。
- 根拠：様式の印字［PS §2.2］、手引きの記載［PS §2.5］。「特親」欄は特定親族ごとの控除額を万円単位で書く［PS §2.4］。
- 限界：端数処理の根拠条文は原文で確認していない［PS §9］。条文の確認は税額のトピックで行う。

## H6：個人番号（マイナンバー）は出力しない。欄値表では空欄として示し、ユーザーが書く

- 内容：第一表の `F02`、第二表の親族・事業専従者の個人番号欄は、欄値表に「記入が必要（出力しない）」として行だけ出す。
- 根拠：申告書の記載事項に個人番号が含まれる（所得税法施行規則第47条第3項第一号・第二十号・第二十一号）［PS §3］。様式に個人番号の欄がある［PS §2.2、§2.3］。
- 設計上の理由（実測・公開資料による裏付けではない）：記録（D3）や中間表現に個人番号を持たせないほうが、漏れたときの被害が小さい。判定には個人番号が要らない。（2026-11-09 独立検証で、仮説文書の中の「I：」の表記を書き換えた）

## H7：申告書第二表のうち住民税・親族の欄は、所得税の出力として出す（住民税の判定とは別）

- 内容：親の申告では、第二表「配偶者や親族に関する事項」に、控除の対象になる親族だけでなく16歳未満の扶養親族も書き（住民税欄に印）、別居の親族は「住民税・事業税に関する事項」の別居欄に氏名・住所を書く。子の申告では、給与以外の所得（事業・業務の雑所得）に係る住民税の徴収方法（`G36`：特別徴収「1」／自分で納付「2」）を書く。これらは所得税の申告書の欄なので、欄値表に含める。`G36` の選択は人の判断として記録する（D4・D12）。
- 根拠：手引きの共通の書き方（※３：年末調整を受けていても16歳未満の扶養親族を省略しない）、第二表の欄［PS §2.3、§2.5］。
- 注記：D14 は住民税を「扶養と非課税の判定のみ」としている。この仮説は住民税額の計算を足すものではない。

## H8：e-Tax の XML を作るのは、次の3つがそろってから

1. ユーザーが e-Tax で申告すると決め、e-Tax の利用規約（第4条を含む）を受け入れる［PS §8.3、TOU §3］。
2. 令和8年分の確定版の仕様書と XML スキーマ（2026-11-25 掲載予定）を、安全を確かめた方法で展開できる［PS §7.2、M §5］。
3. 作った `.xtx` を e-Taxソフト（WEB版）の「作成済みデータの利用」で読み込み、帳票表示（PDF）で欄値表と一致することを確かめられる［PS §7.3］。

- そのときの形：欄値表 → 帳票フィールド仕様書の項目への対応表（年分×帳票バージョンごと）→ XML。対応表は H4 と同じく年分ごとのデータにする。
- 注記：作成コーナーで作った申告書を e-Tax で送る方法（作成コーナーの e-Tax 送信）もある。そのときも e-Tax の利用規約が適用される［TOU §1］。

## H9：令和8年分では「社会保険料控除等の明細書」を出力の候補に加える

- 内容：令和9年1月1日以後に令和8年分の確定申告書を出すときは、社会保険料控除（第74条第2項第5号の社会保険料に係るもの）・小規模企業共済等掛金控除・生命保険料控除・地震保険料控除の証明書類の添付又は提示に代えて、明細書を添付できる（所得税法第120条第6項、令和八年法律第十二号附則第10条）。子が自分で払った国民年金保険料などの控除を申告するときに、記録の明細から作れる。
- 根拠：［PS §3］（条文と附則）、［PS §5.3］（e-Tax の KOB500 バージョン 1.0）、［M §3.2］（紙の様式の一覧にはまだない）。
- 限界：紙の様式（明細書の欄）は未公表。施行規則第47条の2第14項（2027-01-01 版）に記載事項がある［PS §3］ので、欄の候補はそこから取れる。

## H10：紙の様式ID は「`NTA` ＋1桁＋e-Tax の様式ID（6文字）＋ページ（2桁）＋版（4桁）」で、e-Tax の様式ID と同じ英字の O を使う（2026-11-09 独立検証で追加。もとは公開資料の文書 §5.1 にあった推測を移して書き直した）

- 内容：第一表は `NTA1KOA020010230`（KOA020 の1ページ目、版 23.0）、第二表は `NTA0KOA020020230`、医療費控除の明細書は `NTA0KOB560010180`（KOB560 の1ページ目、版 18.0）。
- 根拠：テキスト層のある収支内訳書の様式ID は英字の O（`NTA0KOA110010120`）で、PDF のしおりも `KOA110010120_01`［PS §5.1、MV V2］。e-Tax の帳票一覧の様式ID は英字の O［MV V2］。4桁の部分を版と読むと、令和8年1月受付の e-Tax の一覧の版（KOA020 23.0、KOB560 18.0）と一致する［PS §5.2、MV V2］。
- 反証の条件：第一表・第二表・医療費控除の明細書の様式ID が数字の 0 だと分かった場合（国税庁の AI-OCR 化対象帳票レイアウトの資料などで確かめる）。
- 確かめ方：推測 I8。

## H11：新様式は機械（AI-OCR）で読む前提の作りで、欄コードはそのための印字である（2026-11-09 独立検証で、公開資料の文書 §1.4 にあった推測を移した）

- 根拠：書面提出の注意で、コピーの繰り返しが「読み取りに影響する」とし、枠内への記載と「￥」「円」を書かないことを求めている［PS §1.4］。e-Tax の仕様公開ページに「AI-OCR化対象帳票レイアウトの提供について」がある［PS §7.1］。様式の公表時期の一覧の取得元のファイル名が `ai-ocr.xlsx`［PS §1.1］。
- 意味：欄値表（H1）の欄コードは、国税庁の読み取りの鍵と同じものになる可能性がある。

## H12：e-Tax の仕様書の本文やスキーマはリポジトリに写さない運用が安全（2026-11-09 独立検証で、公開資料の文書 §8.2 にあった推測を移した）

- 根拠：仕様公開ページの注意事項に「各仕様書の内容は著作権の対象となっています」という特記がある一方、ソフトウェアの開発・供給は妨げないとしている［PS §8.1］。国税庁ホームページ利用規約（公共データ利用規約（第1.0版）に準拠）は、別の利用ルールを明示したコンテンツを適用外とする［PS §8.2］。仕様書本体に公共データ利用規約が及ぶかは、この文面だけでは決められない。
