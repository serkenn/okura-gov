## H1. OpenFisca-Core（D6）と判定コアの CLI 形（D7 改）の前提は成り立つ。ただし実装の約束を7つ足す

成り立つ根拠：

- 年の途中・月の途中から始まる期間でも、パラメータは期間の始まりの日の値になり、境目の前日から始まる1年と境目の日から始まる1年で値が切り替わった（R4 未決 U15 は「判定日の値になる」で解決）［OFP］§1、［SRC］§1.1。
- 計算の過程（変数の依存・値、パラメータの名前・参照日・値）を Web API なしで Python から取り出せ、パラメータのメタデータ（出典の参照）にトレースからたどれた。時間の欄を除けば決定的だった［OFP］§4、［SRC］§1.4・§1.5。
- 標準入力の JSON → 標準出力の JSON の CLI が Windows で動き、日本語の名前のまま入出力でき、同じ入力で標準出力のバイト列が同じだった。入力の検査で、OpenFisca に渡る値を int・bool・日付・列挙の名前だけに限れた［OFP］§8。
- 家族5人・年分2・判定日数件で CLI 1回あたり約2秒（うち import が6〜7割）、メモリ約 50 MB［OFP］§9。同じプロセスで evaluate だけを繰り返したときの中央値は 0.16〜1.0 秒（5〜10人、8〜26 シミュレーション）［OFP］§9。〔2026-11-09 独立検証で追加：推測 I4 が使う値を、根拠つきでここに置いた〕

約束（守らないと結果が黙って誤る）：

1. **金額は float を使わない**。OpenFisca の `float` は float32 で、16,777,217 円が 16,777,216 円、20,000,001 円が 20,000,000 円になった。float32 では 2²⁴ 未満でも `floor(x × 0.3)` が1円ずれ、float64 でも `floor(x × 0.29)` などがずれた［OFP］§6、［SRC］§1.6。
   → 金額は `int`（int32）の変数にし、率の掛け算と端数処理は**整数の分子・分母で計算する名前つきの関数**（D13）にする。int の変数の式が小数を返すと 0 方向へ丸められる（負の数で切り捨てと違う）ので、式の戻り値は必ずその関数を通す。int32 の範囲（約 21 億円）と足し算のあふれ（警告なし）は、入力のスキーマの範囲で防ぐ。dtype を int64 に差し替える方法は公開された使い方でなく、入力と読み戻ししか確かめていない［OFP］§6。
2. **パラメータの YAML の日付のキーは「計算する期間の始まりの日から効く日」（適用開始日）にする**。年の途中の施行日をそのままキーにすると、暦年の年の変数ではその年分に旧値が使われた［OFP］§3。年分の全体に効く値は年分の1月1日をキーにし、施行日・出典はメタデータに書く（メタデータは値ごとに取り出せた）。判定日ごとに切り替わる値（健保など）は、切り替わる日をキーにして `year:<判定日>` で引けばよい［OFP］§1。
3. **OpenFisca の入力・期間は、月の1日から始まるものだけを使う**。`year:2025-10-15` で入れた値は黙って `year:2025-10-01` に移り、`year:2025-10-15` では 0 になった。年の変数に暦年で入れた値は `year:2025-10` では見えない（0）［OFP］§2、［SRC］§1.2。
   → 判定日が月の途中でも、入力は月の変数（各月の1日）か暦年の年の変数だけにし、`year:<判定日>` は「パラメータを引く日」と「計算の期間」としてだけ使う。月の合計（`ADD`）は判定日を含む月から12か月になる［OFP］§2.2。これが法令上の「今後1年間」の数え方と合うかは、この文書では判断しない（未決）。
4. **年齢の基準日は明示する**。`year:<判定日>` の `period.stop` は判定日の1年後の前日で、12月31日ではない［OFP］§7。所得税（年分）・健保（扶養認定日が属する年の12月31日［KENPO-src］§5.5）で、基準日を式の中で `periods.period(年).stop` のように明示する。1月1日生まれの扱いなど法的な数え方は、健保については下の〔〕のとおり（基準日の12月31日の終わりの年齢＝翌日の暦の年齢で数える）。所得税については R1・R3 の範囲（ここでは未確認）。
   〔2026-11-09 独立検証で訂正・追記：元は健保を「判定日の属する年の12月31日など」と根拠なしで書いていた。［KENPO-src］§5.5 のとおり、厚生労働省の事務連絡「19歳以上23歳未満の被扶養者に係る認定に関するＱ＆Ａについて」（令和7年7月4日）Q4 は「その年の12月31日現在の年齢で判定する」「年齢は誕生日の前日において加算することから、誕生日が1月1日である者は12月31日において年齢が加算される」とし、日本年金機構の FAQ も「扶養認定日が属する年の12月31日時点の年齢で判定」とする（どちらも原文を取得して確かめた。原文の記録は［SRC］§4。150万円の要件は扶養認定日が令和7年10月1日以降のもの：同 Q8）。この数え方は［OFP］§7 の表の **`年齢_年末の翌日`（12月31日の翌日の暦の年齢）の列と同じ結果**で、`年齢_年末`（12月31日の暦の年齢）とは1月1日生まれだけ食い違う。つまり、基準日を `periods.period(年).stop` にして［OFP］の `暦の年齢` で数えると、1月1日生まれの健保の年齢を1歳少なく誤る。所得税の1月1日生まれの扱いは、この独立検証では一次情報に当たり直していない〕
5. **根拠（D13）は、`get_flat_trace()` をそのまま使わず、木をたどって自分で組み立てる**［OFP］§2.3・§4、［SRC］§1.4：
   - キーは期間を日まで含めて作る（`str(Period)` は日を落とし、別の期間のキーが重なる）。
   - 日付の値を文字列に変換する（そのままでは JSON にできない）。時間の欄（`calculation_time` など）は出さない。
   - パラメータは（名前、参照日）からパラメータの木をたどり、適用開始日・メタデータ（出典の参照）・説明を付ける。
   - **累進税率表を `.calc()` で使うとトレースに記録されない**。税率表を使う式では、使った表を根拠に足す仕組みが要る。（トレースなしのときの `SimpleTracer.record_parameter_access` は何もしない［SRC］§1.4。〔2026-11-09 独立検証で追加：推測 I3 の前提〕）
   - 取引ID は OpenFisca のトレースに入らない。状況の組み立てで（変数・期間・人）→ 取引ID の対応を作って一緒に出す（できた［OFP］§8）。
   - 版：openfisca-core・numpy・法令パッケージの版・パラメータのファイルの SHA-256 を出す（できた［OFP］§8）。
6. **入力は厳密に検査してから OpenFisca に渡す**。検査なしでは、数値の欄の文字列の式（R2）のほかに、`"false"` → true、`"2005-12"` → 2005-12-01、`"20051231"` → 日付でない値、列挙に整数 99 → 計算時に例外、`1e39` → inf、`"nan"` → NaN のように、エラーにならずに意味の違う値になった［OFP］§5。手書きの検査（重複キー・NaN・bool と int の区別・日付の厳密な形・列挙の名前・参照の整合・同じ種類のグループへの重複）で、試した 20 通りの悪い入力をすべて OpenFisca の前で止められた［OFP］§8。
   JSON Schema の検査器のライブラリは今回使っていない。使うなら、そのライブラリの事前の確認が要る（AGENTS.md）。検査の後にも、OpenFisca に渡す値の型を `assert` で確かめる二重の守りにする。
7. **起動は `python -I -X utf8`**。UTF-8 モードでなければ CLI が自分で止まる形にした［OFP］§8、［OF-run］T00。

## H2. beancount（D11）の前提は成り立つ。ただし安全な読み込み関数の条件を R2 のものから改める

成り立つ根拠：

- **走査（`parse_file` で読むだけ）そのものではコードは実行されなかった**（まだ一度も走査していない新しいディレクトリで、R2 の悪い台帳7種）［BCP］A1。
- 走査と loader は同じパーサで同じバイト列を読むので、エンコーディングの細工 24 通りで、走査が受け入れたのにコードが実行される（すり抜け）ものは無かった［BCP］A5。
- 走査は include 先を自分でたどる必要があり、R2 の走査はそうしていた［BCP］A2、［SRC］§2.1。

R2 の走査（`prescan`）で足りなかったこと（コード実行ではなく、資源の使い果たしと情報の漏れ）：

| 問題 | 根拠 | 改めた走査（v2）での扱い |
|---|---|---|
| include の glob が、root の外かを確かめる前に root の外のディレクトリを歩く（5,000 ディレクトリで約3秒。`C:/**` でディスク全体） | ［BCP］A3、［SRC］§2.2 | include の文字列を glob の前に形で検査（相対・`..` なし・ワイルドカードなし・`.beancount`） |
| **1行が長いと `parse_file` の時間が行の長さの2乗で増える**（8 MB の1行で 65 秒、16 MB で 240 秒を超えた） | ［BCP］A6 | 読む前に1行の長さの上限（仮に 64 KiB）で拒否。ファイルの大きさの上限だけでは足りない |
| `include "NUL"` のような通常でないファイルを受け入れる | ［BCP］A7 | 形の検査と `S_ISREG` |
| `option "documents"` と document で root の外のファイル名・存在が読み込み結果に出る | ［BCP］A8、［SRC］§2.3 | `option "documents"` を使わず、document は root の中だけ |
| BOM・NUL・UTF-16 など台帳として正しくないファイルを黙って受け入れる（コードは実行されない） | ［BCP］A5 | 拒否 |

運用の条件：

1. 読み込みのプロセスは **`-I` で起動**する。`-I` が無いと、台帳のディレクトリにある `glob.py` が標準ライブラリより先に import された（台帳のディレクトリをカレントにして `-c` か `-m` で起動したとき。別のディレクトリのスクリプトを指定して起動したときは、代わりにスクリプトのディレクトリが先に探される。`-I` ではどの形でもどちらも探されなかった）［BCP］A9。〔2026-11-09 独立検証で、起動の形の条件を追記〕
2. **読み込みのエラーは失敗として扱う**。メタデータの1行の誤り（日本語のキー、大文字始まり、1文字のキー）で、その取引全体が黙って消え、エラーが1件出るだけだった［BCP］B1。include の循環も loader のエラーとして出る［BCP］A4。
3. 走査と読み込みの間の変更は、読み込みの後に SHA-256 で**検出だけ**できる［BCP］A10。台帳は自分（家族）が書く信頼できるファイルという前提（D3・D11）のもとで、この残りの危険は受け入れる。
4. この PC には gpg が PATH にある［BCP］環境。`.gpg`／`.asc` の include を拒否する規則（v2 では拡張子 `.beancount` 以外を拒否）が実際に必要になる。
5. ファイルのシンボリックリンクの経路は権限が無く試せていない（ジャンクションは拒否できた）［BCP］A7。

## H3. 台帳 → 正規化した取引 JSON のアダプタは、法令の解釈を含めずに作れる

根拠：［BCP］B1〜B3、［SRC］§2.3・§2.4。

- 取引ID（`id`）、日付、金額（`Decimal` を文字列で）、通貨、勘定、メタデータ（日本語の値）、document（root からの相対パスと SHA-256）を JSON にでき、別のディレクトリに写した台帳でも出力が同じだった（決定的）。D5 改の「役割つきの事実」を明細の粒度で作る材料（支払者・受診者・受診日・支払日・証憑）は揃う。
- メタデータの型は Python の型で区別できる（文字列・Decimal・日付・真偽・Amount・None）。ただし**勘定科目・通貨・タグの値は文字列と区別できない**ので、キーごとに型を決めた語彙で検査する（`id` が数になる、`patiant` の書き間違い、重複 ID、存在しない `txid` を検出できた）。
- 台帳の中の算術式（`(50000 + 2000) JPY`、メタデータの `10/3`）は beancount が計算する。数値のメタデータを中間表現に使うなら、`Decimal` の桁（`10/3` は 28 桁）をどう扱うかを決める必要がある。
- 自動で付くメタデータ（`filename` の絶対パス、`lineno`、`__tolerances__`、`__automatic__`）は、出力に絶対パスを出さないために除くか相対化する。

## H4. まとめ：採用の判断は変わらない

- OpenFisca-Core 46.0.1・beancount 3.2.3（＋使わないなら beanquery は不要）の採用（D6・D11）、判定コアを CLI にすること（D7 改）は、上の約束つきで続けてよい。
- 新しく見つかった問題（float32、期間の文字列、トレースのキー、2乗時間の解析）は、どれも**使い方の約束で避けられ**、ライブラリの改変は要らない。致命的な安全上の問題（信頼できる入力だけを渡しても危ない、または避ける手段が無いもの）は見つかっていない。
