## H1. 致命的な安全上の問題の有無（ツールごと）

「致命的」＝信頼できる入力だけを渡しても危ない、または避ける手段が無いもの、と定義して判定する。
信頼できない入力を渡したときの任意コード実行の経路は、すべて「条件」として書く。

| ツール | 致命的な問題 | 信頼できない入力で任意コード実行になる経路（条件） | 根拠 |
|---|---|---|---|
| OpenFisca-Core 46.0.1 | **無い**（本プロジェクトの使い方の範囲で） | パラメータ・テストの YAML（安全でない YAML 読み込み）。国パッケージ・拡張・改正の Python。`--configuration-file` | [OF-src] §2.1・§2.3、[OF-run] T10 |
| beancount 3.2.3（＋beanquery 0.2.0） | **無い**（自分で書いた台帳だけを読む範囲で） | 台帳1行の `plugin` 行で同梱プラグインが `eval`、`insert_pythonpath`＋`plugin`、台帳の隣の pickle キャッシュ。どれも**既定で有効で、止める引数が無い** | [PTA-src] §1.2・§1.3、[BC-run] §4・§6 |
| hledger（未実行） | 未判定（実行していない） | CSV rules の `source ... \| コマンド` がシェルを起動。止める設定が無い。master では journal から rules を include できる | [PTA-src] §2.2 |
| ledger（未実行） | 未判定（実行していない） | Python 対応でビルドした ledger は journal の `python` ディレクティブを実行 | [PTA-src] §3 |

H1 の補足：

- OpenFisca-Core の Web API は、HTTP の要求から任意コード実行に届く経路を見つけなかった。届くのは数値の変数に入れた**文字列の式の評価**（numexpr。禁止パターンの列挙で守っている）だけ（[OF-src] §2.3、[OF-run] T11）。
- 3つの PTA ツールに共通して「台帳（や付属ファイル）＝コード」である。本プロジェクトの記録は自分（家族）が書くものなので、信頼できる前提は成り立つ。ただし、**銀行などからダウンロードした CSV や、他人から受け取った台帳を、そのまま読ませない**ことが条件になる。

## H2. OpenFisca-Core（D6・D7）は採用してよい。ただし `openfisca serve` をそのまま使わない

根拠：[OF-src] §1〜§3、[OF-run] §1〜§2。

- 計算の土台としての OpenFisca-Core（D6）は採用してよい。
  - 保守は活発（直近1年で21リリース、321コミット）。ただしメジャー版が1年に3回上がっているので、**版を固定し、上げるときは自分のテストで確かめる**。
  - 既知の脆弱性は依存の flask-cors 3.0.10 だけ（Web API の extra。OpenFisca が `<4.0` に上限を付けているため直せない）。
    該当する5件は、CORS を全オリジン許可で使う OpenFisca の設定ではほとんど意味を持たない（パスや大文字小文字の照合の問題は、制限する設定のときの問題）か、debug ログのときだけの問題（I）。
- **YAML はコードとして扱う**（[OF-run] T10）。パラメータとテストの YAML をレビューなしに自動生成・自動取り込みしない。
  D9 の「法令の変更を検知して issue を作る」までは問題ないが、**取得した外部データから YAML を自動で書いてコミットする仕組みは作らない**（作るなら安全な読み込みに差し替える。推測 I2）。
- Web API（D7）は、**`openfisca serve` ではなく、`create_app` を自分の薄いラッパーで包んで起動する**のがよい。理由：
  1. Windows では `openfisca serve`（gunicorn）が起動しない（[OF-run] T13）。この PC で動かすなら別の WSGI サーバーか Linux（コンテナ・WSL）が要る。
  2. 既定の CORS が全オリジン許可で、認証も無い（[OF-run] T12f・T12g）。待ち受けが 127.0.0.1 でも、利用者がブラウザで開いた**任意の Web ページから計算 API を呼べる**。
     コアは状態を持たない（D8）ので、盗まれるデータは無い（I）が、
  3. 要求の大きさ・`axes` の数・計算時間に上限が無い（[OF-run] T12i・T12j。`count` 100万で 6秒・763MB、gunicorn のタイムアウトは1200秒）。上の 2 と合わせると、外部のページから PC の資源を使い果たさせることができる（I）。
  4. 数値の変数に入れた文字列が式として評価される（[OF-run] T11・T12o）。中間表現は数値だけのはずなので、受け付ける必要が無い。
  ラッパーでやること：CORS を外す（または自分のクライアントのオリジンだけ）、`Origin` の付いた要求を拒否、本文の大きさの上限、`axes` を拒否、中間表現の JSON Schema で入力を検査（数値の欄に文字列を許さない）、127.0.0.1 だけで待ち受け。→ 推測 I1。
  これは D7（Web API として起動し HTTP + JSON で呼ぶ）を変えるものではなく、起動の仕方の補足。**ただし別の WSGI サーバー（waitress など）を足すなら、それも OSS として事前の確認が要る。**
- Windows で動かすなら `-X utf8`（UTF-8 モード）が必須（[OF-run] T00）。パラメータ・テストの YAML に日本語を書くと、UTF-8 モードなしでは読み込めない。
- spiral（前の期間をたどり続ける参照）はエラーにならず既定値で打ち切られる（[OF-run] T12l）。前年の値を使う計算（繰越など）を書くときは、入力の欠けが黙って 0 になることに注意し、テストで確かめる。

## H3. R4 のモデルは OpenFisca-Core に載る。ただし3つの制約がある

根拠：[OF-src] §3.1、[OF-run] §2.2（T01〜T05、T14）。

載ること（F に基づく）：

- 生計・住民票世帯・健康保険（被保険者と被扶養者）・申告（納税者と扶養親族）のように、**種類の違うグループを複数**定義できる。
- **1人が種類の違うグループに同時に属せる**。「親と生計を一にするが住民票は別、親の健康保険の被扶養者でもある大学生」は、そのまま表せて計算できた（T01）。
- グループの値を人へ、人の値をグループへ、役割を指定して集められる。
- エンティティ名・役割名・変数名は日本語でよい。

制約（R4 のモデル案で避け方を決める必要がある）：

1. **同じ種類のグループには、1人1つのインスタンスにしか属せない**（T02）。
   税の「1人の扶養親族を2人の納税者が重ねて控除できない」は、この制約がそのまま守ってくれる（申告グループの扶養親族に2回書けない）。
   逆に、1人が同じ種類の関係を2つ持つ必要がある概念（あれば）は、別の種類のグループに分ける必要がある。
2. **1つのグループの中で1人は1つの役割しか持てない**（T03）。
   例えば「世帯主であり、かつ国保の加入者」のように役割が重なるなら、(a) 別の種類のグループに分ける、(b) 役割ではなく人の変数（真偽値。期間つき）で表す、のどちらかにする。
3. **所属と役割は期間で変えられない**（T14）。1つのシミュレーションの中では、年の途中の結婚・就職・別居・死亡による所属の変化を表せない。
   避け方の候補：(a) 判定の時点ごとに別のシミュレーションを作る（所得税は12月31日時点の所属、社会保険は判定日時点の所属を中間表現から作る。コアは状態を持たないので回数が増えるだけ）、(b) 所属に当たる事実を月・日の変数（例：「被扶養者である」の月ごとの真偽値）で持つ。→ 推測 I3。

注意：

- グループに書き忘れた人は、エラーにならず**その人だけのグループの「最初の役割」**になる（T04）。最初の役割を「被保険者」「世帯主」「納税者」にすると、書き忘れが黙って誤った判定になる。
  クライアント側で全員の所属を必ず明示する（中間表現のスキーマで必須にする）か、最初の役割を「未設定」のような無害な役割にする。
- 支払った人と受診した人のような**人と人の組の事実**は、OpenFisca の変数（エンティティごとの配列）にそのまま入らない（I：[OF-src] §3.1 の所属の表し方から）。→ 推測 I3。
- 期間：年・月・日・永久の変数を混ぜられ、`year:2025-10` のような月の途中から始まる1年で合計できた（T06）。暦年（所得税）と将来の見込み（社会保険）の両方を表せる見込みがある。
  ただし、**同じ変数に人によって違う粒度（月と年）で入力すると失敗する**（T06x）ので、中間表現では変数ごとに粒度を1つに決める。

## H4. AGPL の範囲

根拠：[OF-src] §1.1（LICENSE の原文。FSF の FAQ は取得できなかった）、[OFJ-src] §4、[PTA-src] §0.2。

- **自分（家族）だけが使い、配布もせず、他人がネットワーク越しに使うこともないなら、AGPL による義務は生じない**。第13条の義務は「改変版」を「ネットワーク越しに利用者とやりとりさせる」ときのもの（LICENSE 540-551行）。
- 自作の税・社会保険パッケージは `openfisca_core` を import し、その上で動く（`Variable` を継承する）。これが「Program に基づく著作物」に当たるかは LICENSE の文だけでは決めきれない。
  **公開や他人への提供をするなら、自作パッケージも AGPL-3.0-or-later で出す前提で考えるのが安全**（仮説。FSF の FAQ の原文で確かめる必要がある）。
- HTTP + JSON で Web API を呼ぶだけの TS などのクライアントは、別個のプログラムで、通信でやりとりするだけなので、AGPL は及ばないと考えられる（仮説。LICENSE 226-232行の aggregate の考え方に近いが、FAQ で要確認）。
- OpenFisca-Core 自体を改変（パッチ）して、他人がネットワーク越しに使える形で動かすなら、改変版のソースを提供する義務がある（第13条）。H2 のラッパーは Core を改変しない形で書けば、この点を避けやすい（I）。
- OpenFisca-Japan（AGPL v3、[OFJ-src] §4）のコードは写さない。考え方だけを参考にする。
- **beancount は GPL-2.0-only**（[PTA-src] §0.2）。GPL-2.0-only と AGPL-3.0 は、1つのプログラムに結合して配布すると両立しない可能性がある（仮説。要確認）。
  記録の集計（beancount を import する）と判定コア（OpenFisca を import する）を**別のプロセスに分け、JSON（中間表現）でだけやりとりする**今の構成（D5・D7）を保てば、この問題を避けやすい。

## H5. plain text accounting は beancount 3（＋beanquery）を、安全な読み込みのラッパーつきで使う

根拠：[PTA-src] §1〜§3、[BC-run] §1〜§7。

推す理由：

- 「誰の取引か」「支払った人と受診した人」を**メタデータ**（`payer:`・`patient:` など）で持ち、beanquery で人 × 期間ごとに集計できた（[BC-run] §3）。中間表現（D5）を作る処理を Python で書ける。
- 取引に自分で振る `id:` メタデータで、D4 の「人の判断」から取引を参照できる（重複は beancount が検出しないので、自分で検査する。[BC-run] §3）。
- 証憑は `document` ディレクティブとメタデータでつなげる（[BC-run] §7）。
- Windows 用の wheel があり、隔離した venv で静的確認と実測を済ませた。hledger・ledger はネイティブのバイナリで、今回は動かしていない。
- 危険な経路（plugin、insert_pythonpath、pickle キャッシュ、台帳の外への include）はすべて**読み込みの入口**にあり、ラッパーで塞げることを実測で確かめた（[BC-run] §4・§6。ただし事前走査そのものが安全なことは実測では切り分けていない）。

条件（守らないと H1 の「致命的でない」が成り立たない）：

1. beancount の台帳は、**必ず自作の読み込み関数を通して**読む：読み込みキャッシュを無効にし（`loader.initialize(False)` など）、`parser.parse_file` で全ファイルを先に走査して `plugin` 行・`insert_pythonpath`・台帳の外への include・暗号化ファイルを拒否する。`bean-check` などの付属コマンドや fava を、この入口を通さずに台帳へ向けない。
2. 外部から来たファイル（銀行の CSV など）は台帳の木の外に置き、取り込みは自作の importer（beangulp を使うなら、それ自体が Python コード）で事実だけを書き出す。

欠点（受け入れる必要がある）：

- 勘定科目名の各成分は大文字か数字で始める必要があり、ルート名は英語だけ。タグ・リンク・メタデータのキーも ASCII だけ（[BC-run] §1・§2）。
  → 勘定科目は英語の階層（`Expenses:Medical` など）にし、日本語は payee・narration・メタデータの値に書く。
  `Expenses:Medical:医療費` は読み込みは通るがライブラリ内部の判定と食い違うので使わない。
- beanquery に JSON 出力は無く、Python API で取り出して自分で JSON にする。

hledger を選ばない理由（再検討の余地あり）：日本語の勘定科目名・JSON 出力の点では hledger のほうが向いている（[PTA-src] §2.1）。
しかし、ネイティブのバイナリで今回は実行して確かめておらず、CSV rules からシェルを起動する経路を止める設定が無い（[PTA-src] §2.2）。
「勘定科目名を日本語で書けること」を重く見るなら、hledger をインストールして [BC-run] の末尾「インストールして確かめるべきこと」を実測してから比べ直す。

ledger を選ばない理由：JSON 出力が無い（[PTA-src] §3）、Python 対応ビルドでは journal がコードになる、直近1年のコミットがほぼ1人に集中している（[PTA-src] §0.2）。

## H6. GovTech 報告書の主張とコードの対応（まとめ）

| 報告書の主張 | 判定 | 根拠 |
|---|---|---|
| OpenFisca-Japan のグループは「世帯」だけ（p.18-19） | 成り立つ | [OFJ-src] §2 (a) |
| 役割は親・子・祖父母で、「子」は未成年（p.19） | 役割の一覧は成り立つ。「子は未成年だけ」はコードで強制されておらず、19歳・22歳の「子」のテストもある | [OFJ-src] §2 (b) |
| 世帯主を特定できず、最も収入が高い人を世帯主とみなす（p.21） | 成り立つ（多くの箇所は収入ではなく所得の順位） | [OFJ-src] §2 (c) |
| 扶養親族の所得要件 48万円（p.13） | OpenFisca-Japan v2.2.0 のパラメータも 48万円のまま（コード上の値。法令上の正しさは R1・R3 の範囲） | [OFJ-src] §2 (d) |
| OpenFisca の出力は数値だけ（p.16） | **Core については成り立たない**（真偽値・列挙・日付・文字列も返る） | [OF-src] §4、[OF-run] T12e |
| 世帯か個人単位でしか計算できない（p.16） | Core については成り立たない（グループを任意に定義できる）。OpenFisca-Japan の定義による制約 | [OF-run] T01 |
| 制度名を階層で管理できない（p.17-18） | 変数については成り立つ。パラメータには階層がある | [OF-src] §3.3 |
| 日本語の変数名が使える（p.8-9） | 成り立つ。ただし Windows では UTF-8 モードが必要 | [OF-run] T00 |

HANDOFF §4 の「OpenFisca-Japan を使わない理由」は、(b) を除いて今のコードでも成り立つ。(b) が成り立たなくても、
グループが同居の「世帯」だけで生計を表せないこと（(a)）と、世帯主の簡略化（(c)）だけで、使わない理由として十分（仮説）。
