## I1. 金額を int にし、率の計算を整数の名前つき関数にすれば、端数の食い違いは起きない

- 前提：[H] H1 の1。
- 推測：`率を掛けて切り捨て(金額, 分子, 分母) = (金額 × 分子) // 分母` のような関数（int64 で計算してから int32 の範囲を確かめる）を、すべての率の計算に使えば、float32・float64 で起きた1円の食い違いは起きず、負の数でも切り捨て・切り上げを関数名どおりに決められる。
- 検証方法：`scripts/IMPL_tools_openfisca_probe.py` の P08 と同じ範囲（0〜20,000,000、3 刻み、率 0.05〜0.57・0.021）で、OpenFisca の式の中からその関数を呼んだ結果が `(x × k) // 分母` と一致することを、D15 の④（性質のテスト）として確かめる。負の金額と int32 の上限近くも入れる。

## I2. 判定日が月の途中でも、`year:<判定日>` を期間にし、入力を月の変数に限れば正しく計算できる

- 前提：[H] H1 の2・3・4。
- 推測：期間を `year:<判定日>` にすると、パラメータと式の選択は判定日の値になり、月の合計は判定日を含む月から12か月になる。入力を月の変数（各月の1日）と暦年の年の変数に限れば、入力が黙って別の期間に移ることは無い。
- 検証方法：判定日を 2025-10-15・2025-09-30・2026-02-28 などにした YAML テスト（D15 の②）を作り、(a) 境目の前後でパラメータの値、(b) 合計に入る月、(c) 年齢の基準日が期待どおりかを確かめる。(c) には 1月1日生まれ（例 2006-01-01）を必ず入れ、健保の年齢が「扶養認定日が属する年の12月31日に加算された年齢」（[H] H1 の4。2025年の判定なら 20 歳）になることを確かめる〔2026-11-09 独立検証で追加〕。状況の組み立てに「年・月の期間の入力は月の1日（年は1月1日）から始まるものだけ」という `assert` を入れ、`year:2025-10-15` の入力を作ろうとすると止まることを確かめる。

## I3. 累進税率表を使ったことも、式から明示的に記録すれば根拠に残せる

- 前提：[H] H1 の5（`.calc()` はトレースに記録されない）。
- 推測：式の中で `人.simulation.tracer.record_parameter_access(名前, 参照日, 値)` を呼ぶ（トレースなしのときは何もしない `SimpleTracer` なので害は無い。〔2026-11-09 独立検証：`SimpleTracer.record_parameter_access` が何もしないことはソースで確かめ、根拠つきで [H] H1 の5 に追記した〕）か、税率表を段ごとの普通のパラメータ（しきい値・率）として持てば、使った表の名前・参照日・値が根拠に入る。
- 検証方法：試験用の国パッケージで両方の書き方を作り、`basis_of` の出力に税率表の名前と参照日が出ること、トレースなしの計算結果が変わらないことを確かめる。`record_parameter_access` は公開された使い方か（ドキュメントにあるか）も確かめる。

## I4. CLI の起動時間の大半は import なので、常駐させれば1回あたり 0.1〜1 秒になる

- 前提：[H] H1（CLI 1回約2秒、うち import が6〜7割。同じプロセスでの evaluate の中央値 0.16〜1.0 秒）。
- 推測：同じプロセスで TaxBenefitSystem を1回だけ読み、要求ごとに `evaluate` だけを呼べば、家族規模の1回の判定は 0.1〜1 秒になる（プロセス内の `evaluate` の中央値から）。〔2026-11-09 独立検証：元は前提の [H] H1 にこの中央値が無かったので、[H] H1 に足した〕ただし常駐は D7 の「HTTP は必要になったときに足す」に当たり、R2 の Web API の注意（CORS・上限・認証）が戻ってくる。
- 検証方法：標準入力から1行1要求の JSON を読み続ける形の試作で、100 回の要求の時間とメモリの増え方を測る。必要になるまでは行わない。

## I5. 改めた走査（v2）＋ `-I` ＋ 読み込みのエラーを失敗とする、で自分の台帳だけを読む範囲の危険は塞がる

- 前提：[H] H2。
- 推測：v2 の走査で、R2 の悪い台帳・エンコーディングの細工・root の外への include・長い行・root の外の document を、コードを実行する前に止められ、残るのは走査と読み込みの間の変更（事後に検出）とシンボリックリンク（未試験）だけ。
- 検証方法：
  1. 開発者モードか管理者で、ファイルのシンボリックリンク（root の中 → 外、root の中 → 中）を作り、v2 が前者を拒否し後者の扱いが意図どおりかを確かめる。
  2. 正しい台帳のバイト列をランダムに1〜数バイト書き換えた台帳を 1 万通り作り（plugin 行を含むものを混ぜる）、「v2 が受け入れたのにコードが実行された」ものが無いことを確かめる（走査と loader の食い違いの探索）。
  3. 実際の台帳（または同じ規模の試験用の台帳）の最長の行を測り、1行の上限（仮に 64 KiB）が実用上の妨げにならないことを確かめる。

## I6. アダプタの語彙と型を JSON Schema で書けば、中間表現の検査と同じ仕組みで扱える

- 前提：[H] H3。
- 推測：アダプタの出力（`impl-probe-tx/0` の形）を JSON Schema で定義し、メタデータのキーごとに型（`string`・`date`・`decimal`）を決めれば、`id` の型違い・書き間違い・重複（重複はスキーマの外で検査）を、中間表現の検査と同じ層で止められる。
- 検証方法：中間表現のスキーマ案の段階で、`normalized_sample.json` と B3 の問題のある台帳の出力に対して、スキーマの検査とスクリプトの検査が同じものを見つけるかを確かめる。JSON Schema の検査器のライブラリを使うなら、先にそのライブラリの安全性を確かめる。
