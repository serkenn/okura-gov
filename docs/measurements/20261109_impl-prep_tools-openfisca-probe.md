## 1. 年の途中・月の途中から始まる期間とパラメータの評価日（R4 未決 U15）（P01）

パラメータ `試験.健保_年収基準`（ダミー）：2020-01-01 から 3333333、**2025-10-01 から 4444444**。

| 期間の指定 | `str(period)` | start〜stop | `parameters(period)` の値 | `parameters(period.stop)` の値 | 式（`formula_2020_01_01`→1、`formula_2025_10_01`→2） |
|---|---|---|---|---|---|
| `2025` | `2025` | 2025-01-01〜2025-12-31 | 3333333 | 4444444 | 1 |
| `year:2025-09` | `year:2025-09` | 2025-09-01〜2026-08-31 | 3333333 | 4444444 | 1 |
| `year:2025-09-30` | `year:2025-09` | 2025-09-30〜2026-09-29 | 3333333 | 4444444 | 1 |
| `year:2025-10` | `year:2025-10` | 2025-10-01〜2026-09-30 | **4444444** | 4444444 | 2 |
| `year:2025-10-01` | `year:2025-10` | 2025-10-01〜2026-09-30 | **4444444** | 4444444 | 2 |
| `year:2025-10-15` | `year:2025-10` | 2025-10-15〜2026-10-14 | 4444444 | 4444444 | 2 |
| `year:2026-04-01` | `year:2026-04` | 2026-04-01〜2027-03-31 | 4444444 | 4444444 | 2 |
| `2026` | `2026` | 2026-01-01〜2026-12-31 | 4444444 | 4444444 | 2 |

- 月の変数：`2025-09` → 3333333、`month:2025-10`・`2025-10` → 4444444。日の変数：`2025-09-30` → 3333333、`day:2025-10-01` → 4444444。
- トレースに記録されたパラメータの参照日は、期間の始まりの日そのもの（`2025-09-30`、`2025-10-15` など。日まで正しい）。`parameters(period.stop)` の式では期間の最後の日（`2026-09-29` など）。

分かったこと（F）：

- **年の途中・月の途中から始まる期間でも、`parameters(period)` は期間の始まりの日の値になる**。境目（2025-10-01）の前日から始まる1年（`year:2025-09-30`）は旧値、境目の日から始まる1年は新値。期間の途中に境目があっても、期間の途中で値は切り替わらない。
- 式（`formula_YYYY_MM_DD`）の選択も期間の始まりの日で決まる。
- 期間の最後の日など別の日の値が要るときは、式の中で `parameters(期間.stop)` のように日付を渡せば、その日の値になる。

## 2. 年の途中から始まる期間と入力（P02、P05b）

### 2.1 入力した期間と計算する期間が違うとき

| 入力 | 計算 | 結果 |
|---|---|---|
| 年の変数 `年額収入_円` に `2025`: 1000 | `2025` | 1000 |
| 同上 | `year:2025-10` | **0**（エラーにならず既定値） |
| 同じ変数に `2025`: 1000 と `year:2025-10`: 500 | `2025` / `year:2025-10` / `year:2025-04` | 1000 / 500 / 0（両方入り、別の期間として持つ） |
| 月の変数（`set_input_divide_by_period`）に `year:2025-10`: 1200 | `2025-09` / `2025-10` / `2026-09` / `2026-10` | 0 / 100 / 100 / 0（2025-10〜2026-09 に 12 等分） |

### 2.2 月の変数を、月の途中から始まる年の期間で合計（`ADD`）したときの月

月ごとに別のビット（2025-08 から 2026-11 まで 16 か月）を入れ、合計から足された月を読み取った。

| 期間 | start〜stop | 足された月 |
|---|---|---|
| `year:2025-09-30` | 2025-09-30〜2026-09-29 | **2025-09〜2026-08**（12か月） |
| `year:2025-10-01` | 2025-10-01〜2026-09-30 | 2025-10〜2026-09（12か月） |
| `year:2025-10-15` | 2025-10-15〜2026-10-14 | 2025-10〜2026-09（12か月） |
| `year:2025-10-31` | 2025-10-31〜2026-10-30 | 2025-10〜2026-09（12か月） |

→ 合計に入るのは「始まりの日を含む月」から12か月（[SRC] §1.3 の `first_month`）。始まりの日が月の途中でも、その月の全体が入り、最後の月の途中までの日は入らない。

### 2.3 期間の文字列表現で日が落ちる

| 期間の指定 | `str(periods.period(...))` |
|---|---|
| `year:2025-10-01` | `year:2025-10` |
| `year:2025-10-15` | `year:2025-10` |
| `month:2025-10-15` | `2025-10` |
| `day:2025-10-15` | `2025-10-15` |
| `year:2025-01-15` | `2025` |

その影響：

- **dict の situation に `year:2025-10-15` で入れた値は、`year:2025-10-01` の値として登録され、`year:2025-10-15` で計算すると 0 になる**。`year:2025-10-01` と `year:2025-10-15` の両方を入れると、後の値（`year:2025-10-15` の 200）が `year:2025-10-01` に入り、`year:2025-10-15` は 0。エラーも警告も出ない（[SRC] §1.2 の `input_buffer` のキー）。
- 同じシミュレーションで `year:2025-09` と `year:2025-09-30` を計算すると、計算結果とトレースの木（`Period` を持つ）は2つに分かれるが、`get_flat_trace()` のキーは `健保_基準値_期間末<year:2025-09>` の1つにまとまる（最初の記録だけが残る）。
- `tracer.browse_trace()` で木をたどり、キーを `{単位}:{開始日}:{長さ}` で自分で作ると（CLI の `basis_of`）、`健保_基準値_期間末<year:2025-09-01:1>` と `<year:2025-09-30:1>` に分かれた。

## 3. 施行日をキーにしたパラメータと、適用開始日をキーにしたパラメータ（P03）

| 年の変数の期間 | 施行日キー（2020-01-01: 1111111、**2025-12-01**: 2222222） | 適用開始キー（2020-01-01: 1111111、**2025-01-01**: 2222222、`施行日: 2025-12-01` はメタデータ） |
|---|---|---|
| `2024` | 1111111 | 1111111 |
| `2025` | **1111111** | **2222222** |
| `2026` | 2222222 | 2222222 |
| `year:2025-12` | 2222222 | 2222222 |

- 施行日（年の途中）をそのままキーにすると、暦年の年の変数（`2025`）は1月1日の値を引くので、**その年分には旧値が使われる**。年分の全体に新値を使うなら、キーを年分の初日にし、施行日はメタデータに書く必要がある。
- メタデータは値ごとに取り出せた：`2025-01-01` → `{"reference": "試験用（ダミー）#新", "施行日": "2025-12-01", "適用": "2025年分以後（ダミーの説明）"}`。YAML の日付はメタデータの中でも文字列になった。

## 6. 精度と端数（P08）

- float（float32）の入力：16777216→16777216.0、**16777217→16777216.0**、**20000001→20000000.0**、**123456789→123456792.0**。int（int32）：20000001→20000001、2147483647→2147483647。
- numpy の型の昇格：float32 の配列 × 0.1 → float32、int32 の配列 × 0.3 → float64。int32 の配列どうしの足し算 2147483647 + 1 → **-2147483648**（あふれても警告なし）。
- int の変数の式が小数を返したとき：1000001 × 0.3 = 300000.3 → 300000、-1000001 × 0.3 → **-300000**（切り捨てなら -300001。0 方向への丸め）。
- `floor(x × r)` と、整数演算 `(x × k) // 分母` の比較（率は例示。法令の率ではない）：

| 率 r | x＝1,000 の倍数（20,001 点）：float32 / float64 の食い違い | x＝3 刻み（6,666,667 点）：float32 の食い違い（うち x < 2²⁴） | 同：float64 の食い違い | 例（x, 計算値, 正確な値） |
|---|---|---|---|---|
| 0.05 | 0 / 0 | 53,713（0） | 0 | float32：16777239 → 838862（正確 838861） |
| 0.1 | 0 / 0 | 53,713（0） | 0 | |
| 0.2 | 0 / 0 | 107,426（0） | 0 | |
| 0.3 | 0 / 0 | **1,438,787（955,370）** | 0 | float32：3495273 → 1048582（正確 1048581） |
| 0.4 | 0 / 0 | 741,709（419,431） | 0 | float32：10485762 → 4194305（正確 4194304） |
| 0.29 | 0 / **5,622** | 384,985（176,880） | **18,749** | float64：1500 → 434（正確 435）、3000 → 869（正確 870） |
| 0.57 | 0 / **11,301** | 1,301,517（798,036） | **37,679** | float64：300 → 170（正確 171） |
| 0.021 | 0 / 0 | 45,079（27,937） | 0 | float32：1562619 → 32815（正確 32814） |

（すべての数は `results.json` の `P08_精度と端数`。〔2026-11-09 独立検証：表の食い違いの数・x<2²⁴ の数・例は、numpy を使わない別の計算（float32 の丸めを `array('f')` で再現）ですべて同じ値になった。`scripts/IMPL_tools_verify.py` の V4〕
float64 の食い違いは、積 x × r を倍精度に丸めた値が整数のちょうど手前（例 1500 × 0.29 → 434.99999999999994）になり、切り捨てで1小さくなるもの。〔独立検証で訂正：元は「0.29 が2進数で 0.29 よりわずかに小さく表されるため」としていた。0.3 も2進数では 0.3 より小さい（0.299999999999999988897…）が、この範囲で float64 の食い違いは 0 件だった。率が小さく表されることは必要だが、それだけでは決まらず、積を丸めたときに整数に戻るかで決まる（V4 の「率の2進表現」「倍精度の積の例」：10 × 0.3 → 3.0、3000 × 0.3 → 900.0）〕）

- dtype を int64 に差し替えた変数（`__init__` で `self.dtype = np.int64`。公開された使い方ではない）：dtype は int64 になり、3000000000 を入れて読み戻せた。それ以外の経路（式・集計・トレース）での挙動は確かめていない。

| 2006-01-02 | 19 | 19 | 19 | 20 |
| 2004-02-29 | 21 | 21 | 21 | 22 |

- 書き方：生年月日は `value_type = date`・`ETERNITY`、年齢は年の変数で `period.stop`（暦年なら 12月31日）を基準日にして numpy の `datetime64` で数えた（スクリプトの `暦の年齢`）。「年末の翌日」の書き方（`period.stop.offset(1, DAY)`）を使うと 1月1日生まれだけ結果が変わる。どちらが法的に正しいかは、ここでは確かめていない。
- **`year:<判定日>` の期間で `period.stop` を使うと、判定日から1年後の前日を基準にした年齢になる**（上の表の最後の列）。「判定日の属する年の12月31日」が要るときは `periods.period(period.start.year).stop` のように明示する必要がある。
- `ETERNITY` の変数（生年月日）は年の期間で引いても値が返った。
- 列挙：入力は名前（`"給与"`）、出力は `decode_to_str()` で名前の文字列。入力がない年は既定値（`なし`）。式の中で `人("所得区分_入力", period) == 所得区分.給与` で比べられた。内部は index（給与 0、事業 1、なし 2）。列挙の配列で添字をつけてパラメータを引けた（`区分別控除` → 10、20、0）。

## 8. 判定コアの CLI 形（標準入力の JSON → 標準出力の JSON）（P10）

`impl_cli.py`（スクリプトが一時ディレクトリに書き出す最小形）：

1. UTF-8 モードでなければ終了コード 4。
2. 標準入力をバイト列で 1,000,000 バイト＋1まで読み、超えたら拒否。UTF-8 として厳密に復号し、BOM を拒否。`json.loads` に `object_pairs_hook`（重複キーを拒否）と `parse_constant`（NaN・Infinity を拒否）を渡す。
3. 手書きの検査（JSON Schema の検査器の代わり。venv に入っている標準ライブラリだけ）：知らないキー・足りないキーを拒否、整数は `type(x) is int`（bool を弾く）で範囲 0〜2,000,000,000、日付は `YYYY-MM-DD` の正規表現＋`date.fromisoformat`、列挙は決まった名前だけ、人のIDは参照の整合と制御文字の禁止、同じ年分に1人が2つの扶養所属、同じ日に1人が2つの健保・婚姻に属するのを、人の名前つきで拒否。
4. 判定の時点ごと（所得税は年分ごとに 12月31日、健保は判定日ごと）に situation を組み立て、**OpenFisca に渡す前に、値が int・bool・`datetime.date`・列挙の名前だけであることを `assert` で確かめる**。
5. 結果（値）と根拠（変数の依存・値、パラメータの名前・参照日・値・適用開始・メタデータ、入力の取引ID、版：openfisca-core・numpy・国パッケージの版・パラメータのファイルの SHA-256）を、キーを並べ替えた JSON で標準出力へ。時間の計測は標準エラーへ（`--timing`）。

結果：

- 正常な入力（家族5人、年分2、健保の判定日3 → 5シミュレーション）：終了コード 0、出力 39,720 バイト、wall 3.06 秒（うち import 2.26 秒。この回は PC の負荷で遅かった）。日本語の人のID・変数名・メタデータがそのまま入出力できた。
  - `健保_試験` の `year:2025-09-30` は `健保_基準値` 3333333、`year:2025-10-01` は 4444444（境目の前後で別の値。根拠のパラメータに `適用開始: 2025-10-01`、`施行日: 2025-10-01`、`reference` が付いた）。
  - 入力の取引ID：`月額収入_円<2025-01>` → `{"子1": ["tx-2025-01-c1"], …}` のように、状況を組み立てるときに中間表現の取引IDを変数・期間・人に対応づけて出せた（OpenFisca のトレースには取引IDは入らないので、組み立て側で持つ必要がある）。
- **同じ入力で2回実行した標準出力の SHA-256 が同じ**（時間を標準エラーに分けたため）。
- 検査で止めた入力（20件。すべて終了コード 2、`{"ok": false, "エラー": [{"場所": …, "内容": …}]}`）：

## 10. 分からなかったこと・確かめていないこと

- 実際の規模の国パッケージ（変数・パラメータが数百）での TaxBenefitSystem の読み込み時間と評価時間。今回の試験用パッケージ（変数 34、パラメータ 5 ファイル）では、CLI の中の読み込みが 0.03〜0.06 秒、プローブのプロセス内の初回の読み込みが 0.195 秒（`results.json` の `tbs_load_seconds_in_process`）だった。
- dtype を int64・float64 に差し替えた変数が、式・集計（`sum`・`ADD`）・改正（Reform）・YAML テストでも正しく動くか。
- `DIVIDE` や `set_input_dispatch_by_period` の経路での、月の途中から始まる期間の扱いとトレースの記録。
- 累進税率表（`ParameterScale`）を引いたことをトレースに残す方法（今回は記録されないことだけを確かめた）。
- 時間の値は他のプロセスが動いている PC で測ったので、絶対値ではなく桁の目安。
