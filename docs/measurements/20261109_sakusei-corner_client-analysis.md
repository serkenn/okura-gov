## 0. ユーザーの判断と前提

- **ユーザーの判断（2026-11-09）**：e-Tax に送信しない利用は、国税電子申告・納税システム（e-Tax）の利用規約の適用範囲外である。この判断に基づいて、作成コーナーのクライアント側の解析を行う。
  - 根拠に使った規約の原文は `docs/public-sources/20261109_nta-software_terms-of-use.md`。作成コーナーの利用規約は「作成コーナーから直接国税電子申告・納税システムにデータを送信した場合には、『国税電子申告・納税システムの利用規約』が適用されます。」としている。e-Tax の利用規約の「システム利用者」は「本システムを利用して申告等手続又は国税の納付手続を行う者」（第２条第二号）。
- **前提（2026-11-09）**：この解析は、e-Tax 利用規約上の「システム利用者」に当たらない立場で行った。（2026-11-18：公開にあたり、個人の事情の記述を前提の形に改めた）
  - この前提は、ユーザー本人が 2026-11-09 に明言したものとして、調査を依頼したエージェント（コーディネーター）から伝えられた。この解析の担当者が、ユーザー本人から直接聞いたものではない。
- 注意（2026-11-09、`docs/public-sources/20261109_nta-software_terms-of-use.md` の旧「ユーザーの判断」節から移した）：今後ユーザーが e-Tax を使って申告すると「システム利用者」になる。その時点以降の解析については、改めて検討する。
- この解析で行ったのは、通常のブラウザが画面を開いたときに取得するのと同じ静的ファイル（HTML、JavaScript、テキスト、xlsx）の GET だけ。e-Tax へのログイン・送信、マイナンバーカード連携、フォームへの入力・送信（POST）はしていない。取得した JavaScript は実行していない。

### 0.1 作成コーナー上の利用規約の現行版（F）

作成コーナーのトップから開ける利用規約のページ（`/kyoutu/ky/st/ccw0400`、画面番号 CC-AX-040）を取得した（§3 の表の #14）。

- 末尾の日付は「最終更新日：令和７年１月６日」（1315行目、文字オフセット 38127）。`docs/public-sources/20261109_nta-software_terms-of-use.md` で確認した PDF（令和５年４月１日改定後）より新しい。
- 「６ 禁止行為」の項目は、PDF の版と同じく、リバースエンジニアリング・解析を名指しで禁じる項目はない。包括的な項目（「第三者又は国税庁に不利益若しくは損害を与える行為又はそのおそれのある行為。」「その他国税庁が不適切と判断する行為。」など）がある。この版では、「税理士等以外の方が他人の確定申告書の作成などを業（無償の場合を含みます。）として行うことは法律で禁止されています。」という一文が禁止行為の並びに入っている。
- 前文に「本利用規約の変更を行おうとするときは、緊急の場合を除き、変更の効力発生日の７日前までに…作成コーナートップ画面のお知らせに掲載し公表する」とある。

## 5. 結論：税額・控除額の計算はブラウザ側かサーバー側か

**結論（I、根拠は下の F）：作成コーナーの税額・控除額の計算は、ブラウザ側（JavaScript）ではなくサーバー側で行われている。** 少なくとも、フォームの送信なしで取得できる静的ファイルには、計算処理も基準額の表もない。

根拠（F）：

1. 取得した HTML・JS・テキスト（§3 の 44件から #1 robots.txt の 404 ページ、#2 `/` のリダイレクト用ページ、#43 xlsx を除いた 41件）で、金額の書き方（`[0-9]{1,3},[0-9]{3}円`、`[0-9]万円`、`[0-9]円`）と、令和7年分の改正に関係する基準額の数字（650000、550000、580000、480000、950000、1230000、1500000）を探した。一致は1件だけで、トップの消費税の説明文の「1,000万円」（トップ 1319行目 @35062）だった。基準額の表は見つからなかった（`scripts/results/SAKUSEI_grep/no_amounts.json`）。
2. 所得税アプリの共通 JS 25本に定義されている関数は 207個（サードパーティの `jquery.autotab.min.js` の関数を含む。`scripts/results/SAKUSEI_grep/syotoku_common_functions.json` に関数名と位置）。名前と中身から見て、どれも画面の表示（ダイアログ、タブ、スクロール）、入力の補助（カンマ・ハイフンの付け外し、全角・半角の変換、自動タブ移動）、日付と元号の変換、入力の形式チェック、ブラウザの判定のどれかだった。給与所得控除・基礎控除・扶養控除などの税の計算をする関数はなかった。
3. 計算らしい処理は §6 の4つ（一覧の合計、合計から行の値を引く、10のべき乗の倍数かのチェック、年末時点の年齢）だけで、どれも基準額を含まない。
4. 入力チェックの一部はサーバーへ問い合わせている。`requiredCheckAjax`（`taCheckAjax.js` 4行目）は、フォームの全項目（名前に `_zip` を含む項目だけは空にする）を **POST でサーバーへ送り**、サーバーから返ったエラーの一覧（エラーの種類 `E` など、対象の項目名）を画面に出す。項目名は `inOutDto.` で始まる形で扱われている（36〜37行目ほか）。
5. 画面の遷移はフォームの POST で、URL に `jsessionid` が付く（医療費集計フォームの画面 200行目、配当集計フォームの画面 190行目の `form` の `action`）。画面の HTML はサーバーがセッションごとに組み立てている（Cookie を送らずに取得した2つの画面には、別々の `jsessionid` が埋め込まれていた）。

推測（I）：

- 所得税の入力画面は、送信のたびにサーバーで計算して結果を HTML に埋め込んで返す作り（`inOutDto` という名前と `jsessionid` の付け方から、Java のサーバーアプリと思われる）。所得税の入力画面そのものの JS は見ていないので、入力画面に画面固有の計算処理（たとえば入力中の小計の表示）があるかどうかは確かめていない。ただし、共通 JS に計算の部品（`taCalcUtil.js` は 758バイトで一覧の合計だけ）しかないことから、基準額を使う計算がブラウザ側にある可能性は低いと考える。
- 依頼の条件（サーバーへの入力の送信は禁止）により、これ以上は深追いしない。

## 7. 年分の切り替えの仕組み

- 所得税アプリは年分ごとに別のパスに置かれている：令和7年分は `/r7/syotoku/`、お知らせは `/r7/osirase_top.txt`、よくある質問は `/r7yokuaru/`、手引きは `/r7/tebiki/`（F：取得した画面のリンク）。
- 所得税アプリの画面の URL には `taxYear=25` が付く（F）。25 は 2025年（令和7年）の西暦の下2桁と思われる（I）。
- 共通 JS の中に年分で値を切り替える表や分岐は見つからなかった（F：`taxYear`・「年分」を検索して、和暦の表示の書式（年／年分／年度）以外の一致がない）。
- 推測（I）：年分ごとにアプリ全体を別に配備し、基準額は（ブラウザに出てこない）サーバー側の各年分のアプリの中に持っている。ガイドの「令和３年分から令和７年分」の作成は、`/r3/`〜`/r7/` のような年分ごとのアプリで行っていると思われるが、`/r3/`〜`/r6/` のパスは取得した画面のリンクには出てこなかったので確かめていない。

## 8. 法令の一次情報との照合

基準額・計算式はブラウザ側に見つからなかったので、R1 の基準額（`docs/public-sources/20261109_R1-laws_income-tax.md`）と照合できるものはない。

照合できたのは年齢の計算だけ：

| 観察（`jsGetAge`） | 法令（R1 の整理による） | 結果 |
|---|---|---|
| 対象の年の12月31日時点の満年齢を、「対象の年 − 生まれた年、1月1日生まれは +1」で出す | 年齢は出生の日から起算し、民法第143条を準用する（年齢計算ニ関スル法律 第1項・第2項）。期間は起算日に応当する日の前日に満了する（民法第143条第2項）。扶養親族・特定親族などに当たるかは、その年12月31日の現況による（所得税法第85条第3項）。出典：`docs/public-sources/20261109_R1-laws_social-insurance-age-records.md` §3、`docs/public-sources/20261109_R1-laws_income-tax.md`（第85条第3項）、本文は `scripts/results/R1_egov_articles/nenrei_2026-11-09.txt`・`minpo_2026-11-09.txt`・`shotoku_2026-11-09.txt` | **一致**。1月1日生まれの人は、誕生日の前日（前年の12月31日）に1つ年をとるので、対象の年の12月31日には「対象の年 − 生まれた年 + 1」歳になる。それ以外の日に生まれた人は、対象の年の誕生日の前日までに年をとっているので「対象の年 − 生まれた年」歳。式はこれと同じ |

- `jsGetAge` に渡される「対象の年」が申告する年分なのか、どの画面で使われているのか（扶養親族の年齢の判定に使われているのか）は、入力画面を見ていないので分からない。年の中途で死亡・出国した場合（その時の現況で判定する）の扱いも、この関数にはない。

## 10. 気づいたこと・懸念

- **サーバー側のセッション**：所得税アプリの画面（#16、#17）と `top_web`（#15）を GET したとき、サーバーはセッションを作り、URL に `jsessionid` を埋め込んで返した（Cookie を送らない取得なので、取得のたびに新しいセッションになる）。作られたセッションは3つ程度で、負荷は小さいと考えるが、同じ取得を繰り返すとその分セッションが増える。取得した HTML にはセッション ID が含まれるので、HTML をリポジトリに入れないこと（入れていない）。
- **サードパーティのスクリプト**：トップ（102行目）と `top_web`（106行目）は、別ドメインの `https://keisan.couix.jp/couix.loader.js` を読み込んでいる（F）。画面の「チャットボットに質問する」の部品と思われる（I）。対象ホストの外なので取得も解析もしていない。
- **よくある質問の検索フォーム**の送信先も別ドメイン（`https://yokuarusearch.wnsearch.jp/scs/web/sf1.wn`）（F）。送信していない。
- **規約**：作成コーナーの現行の利用規約（令和７年１月６日）にも、解析を名指しで禁じる条項はない（§0.1）。ただし包括的な禁止項目（「国税庁に不利益…を与える…おそれのある行為」「その他国税庁が不適切と判断する行為」）がある。今回は通常のブラウザと同じ GET を 44件、2.5秒間隔で行っただけで、負荷や不利益を与える取得ではなかったと考える。e-Tax の利用規約の扱いは §0 のユーザーの判断による。
- **入力画面へ進む方法がない**：所得税の入力画面は「提出方法の選択」（書面を選ぶ場合も含む）でフォームを POST しないと開けない。書面を選んで進むことは e-Tax への送信ではないが、今回の条件（フォームの送信をしない）では進めない。進めるかどうかはユーザーの判断が必要。
- **robots.txt はない**（404）。`/`（`/r7/ta_top.htm`）の HTML には `<meta name="robots" content="NOINDEX,NOFOLLOW">` がある（F。パソコン用トップ `/kyoutu/ky/sm/top` にはない）。検索エンジン向けの指定で、今回の取得（人の調査のための少数の取得）を禁じるものではないと考える（I）。
