# R2 採用の仮説から導いた推測と、その検証方法

- 作成日：2026-11-09（R2 担当）
- 種別：推測。前提とする仮説は `docs/hypotheses/20261109_R2-tools_adoption.md`（以下 [H]）。
- 文中の [OF-src]・[OF-run]・[BC-run] は [H] の冒頭で定義した文書の略号（[H] が根拠として参照しているもの）。
- どれもまだ検証していない。検証したら、結果を `docs/measurements/` に書き、ここに参照を足す。

## I1. Web API のラッパーで、外部ページからの呼び出しと資源の使い果たしを防げる

- 前提：[H] H2（CORS が全許可、上限が無い、文字列の式が評価される）。
- 推測：`openfisca_web_api.app.create_app(tbs)` が返す Flask アプリに対して、Core を改変せずに次をすれば、[OF-run] の T12f・T12g・T12i・T12j・T12o の危険は塞げる。
  - WSGI ミドルウェアで `Origin` ヘッダの付いた要求を 403 にする（自作の TS クライアントはブラウザから呼ばない前提。ブラウザから呼ぶなら許可するオリジンを1つに限る）。
  - `app.config["MAX_CONTENT_LENGTH"]` を設定する（例：1MB）。
  - `/calculate` の前に、中間表現の JSON Schema で検査する（`axes` キーを拒否、数値の欄は number だけ、人数の上限）。`/trace` を使わないなら塞ぐ。
  - CORS の応答ヘッダを付けない（flask-cors の after_request を外すか、ミドルウェアで消す）。
  - 127.0.0.1 だけで待ち受ける。
- 検証方法：`scripts/R2_openfisca_check.py` の T12 系をラッパーに向けて再実行するスクリプトを作り、
  外部オリジンの事前確認・POST が拒否されること、30MB の本文が 413 になること、`axes` と文字列の式が 400 になること、普通の計算（T12e）は同じ結果になることを確かめる。
  Windows で使う WSGI サーバー（waitress など）を選ぶなら、その OSS の静的確認を先に行う。

## I2. YAML の読み込みを安全な読み込みに差し替えられる

- 前提：[H] H2（YAML はコード。自動生成するなら差し替える）。
- 推測：`openfisca_core.parameters.helpers._load_yaml_file` は呼ぶたびに `config.Loader` を参照する（[OF-src] §2.1、`helpers.py:45-47`）ので、
  `openfisca_core.parameters.config.Loader` を `yaml.CSafeLoader`（または SafeLoader）を継承したクラスに差し替え、Core が登録している2つのコンストラクタ（日付を文字列で返すもの、キーの重複を拒否するもの。`config.py:29-` ）を同じように登録すれば、パラメータの読み込み結果は変わらず、`!!python/...` タグは拒否される。
  テストの YAML も `openfisca_core.tools.test_runner.Loader` を差し替えれば同じ（`test_runner.py:129` でモジュールの変数になっている）。
- 検証方法：差し替えたうえで [OF-run] の T00・T07・T09 が同じ結果になり、T10 で一時ファイルが作られない（`ConstructorError` になる）ことを確かめる。
  OpenFisca の版を上げたときに差し替えが効いているかを確かめるテストも置く。

## I3. R4 のモデルの3つの制約は、次の書き方で避けられる

- 前提：[H] H3（同じ種類のグループは1つ、役割は1つ、所属は期間で変わらない、人と人の組は入らない）。
- 推測：
  1. **所属の時間変化**：判定の時点ごとに中間表現から別々のシミュレーション（別々の `/calculate` 要求）を作る。所得税（12月31日の現況）は年に1回、社会保険の被扶養者は判定日ごと。
     年の途中の所属の変化で計算が変わるもの（月割りの計算など）は、所属の代わりに「その月に被扶養者である」のような月の真偽値の変数で入れる。
  2. **役割の重なり**：グループの種類を制度ごとに分ける（生計、住民票世帯、健康保険、申告…）。1つの種類の中で重なる性質（「世帯主」でもあり「国保の加入者」でもある、など）は、役割ではなく人の真偽値の変数にする。
  3. **支払った人 × 受診した人**：中間表現では組（支払者 ID、受診者 ID、金額）を持つ。判定コアに渡す前に、クライアント側の機械的な変換で「支払者ごと・受診者が申告グループ（または生計グループ）の誰か」の合計に直して、人の変数として入れる。
     どのグループに属するかは、同じ要求の中で入力として与えた所属だけを使うので、この変換に新しい法的な判断は入らない（ただし D5 の「中間表現を作る処理は法令の解釈を含まない」の範囲に収まるかは、R4 とユーザーで確認する）。
     もう1つの案は、支払者を役割（`max: 1`）とする「医療費の負担」グループを作ること。ただし1人の受診者の医療費を2人が別々に払っていると、同じ種類のグループに2回書けない（T02）ので、この案は破綻する場合がある。
- 検証方法：R4 のモデル案が出たら、そのエンティティ定義で `scripts/R2_openfisca_check.py` と同じ形の試験パッケージを作り、
  「別居の大学生（生計は同じ・住民票は別・健保の被扶養者）」「年の途中で就職して被扶養者から外れる子」「父が子の医療費を払い、母も一部を払う」の3つのシナリオを YAML テストで書いて、期待どおりの値になるかを確かめる。

## I4. この PC（Windows）では、OpenFisca を UTF-8 モードと gunicorn 以外のサーバーで動かすか、Linux で動かす必要がある

- 前提：[H] H2（`openfisca serve` は Windows で起動しない、UTF-8 モードが必須）。
- 推測：(a) Windows ネイティブ：`python -X utf8` ＋ I1 のラッパー ＋ gunicorn 以外の WSGI サーバー。(b) Linux：コンテナか WSL のディストリビューションで `openfisca serve --bind 127.0.0.1:...`。
  (b) では gunicorn 22.0.0 のまま使うことになり、その版の確認（OSV では該当なし、[OF-run] §1）で足りる。
- 検証方法：(b) は Linux 上で `openfisca serve` を起動し、`ss -ltnp` などで待ち受けアドレスが 127.0.0.1:5000 であること、ワーカー数、1200秒のタイムアウトを実測する（[OF-run] §3 の残り）。
  (a) は I1 の検証と同時に行う。

## I5. beancount の安全な読み込み関数を、記録層の唯一の入口にできる

- 前提：[H] H5（条件 1・2）。
- 推測：[BC-run] §4 の `prescan` を、キャッシュ無効化と合わせて1つの関数にまとめ、記録層のすべての処理（集計、検査、中間表現の生成）がそれを通るようにすれば、
  台帳の木の中に悪いファイルが混じっても、コードが実行される前に拒否できる。
- 検証方法：[BC-run] の 4a〜4e・6 の悪い台帳を**まだ一度も走査していない新しいディレクトリ**に作り、その関数で読ませて、マーカーが作られずに拒否されることを確かめる（[BC-run] で切り分けられなかった「走査そのものが安全か」を確かめる）。
